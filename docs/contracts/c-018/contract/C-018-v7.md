## Форма ссылки на чужой контракт

**Этот контракт принимает правило C-001 §0.5.** Живая ссылка — та, что стоит в утверждении в настоящем времени и не помечена датой, — называет **контракт и его правило**: имя контракта, номер раздела, пункта, инварианта. **Номера чужого издания в ней нет.** Номер издания законен и обязателен в **датированном** месте: в абзаце ломающих изменений, в помеченном снимке, в записи о выполненной проверке, в историческом разборе; датированное место не правится — оно верно на свою дату.

**Правило принимается, а не наследуется:** C-001 §0.5 говорит о тексте C-001 и чужой текст не обязывает. **Цена принятия названа:** читатель живой ссылки не узнаёт из неё, по какому изданию утверждение проверялось; узнаёт он это из записи о проходе в отчёте об издании, ценой одного перехода.

**1. §8.2, три клаузы по** `recordingPolicy`**: было правило без названного субъекта, отвечавшее на один вход двумя способами в одном предложении, — стал названный субъект и один ответ.** **Было:** «`.auto` — … Спрос не поднимается»; **Кого ломает:** К29 (строка 1) и всякий критерий, подающий команду `skip` или ответ `.skip` (К31, К32, К37), — прибавляется вектор «перезапуск внутри окна»; К78 (§10, перечень Б) — строка стала следствием; критерий на инвариант 24, которого дельта по v2 ещё не написала, пишется сразу по новой редакции — **это экономия, а не двойная работа**, и ради неё дельта критериев и ждёт v3.

**1. Окно заведения сессии: было** `now < armAt` **— стало** `now ≤ graceEndsAt`**; строка 1 §7 разошлась на три.** **Было** (§7, строка 1): «заведение сессии по событию: `e.isAllDay == false`, `e.isCancelled == false`, `now < armAt` (§9.1)». **Стало:** строки 1, 1а и 1б — **одно** условие заведения (§9.1) и три состояния заведения по `now`. **Что чинится:** событие, у которого `armAt` прошёл, а `graceEndsAt` ещё нет, попадало в `plan(now:)` и сессии не получало; инвариант 17 на такой строке плана был неисполним ни одной верной реализацией. **Кого ломает:** К29 (строка 1) и К74 (инвариант 17) перечня — обе их оговорки о собственной неполноте снимаются; К30 (строка 2) — появилась верхняя граница; заводится нужда в критериях на строки 1а и 1б. **Ответы меняются.**

**2.** `PowerActivityToken`**: было «при выходе из** `stopping`**» — стало «при выходе из множества** `{recording, stopping}`**».** **Было** (инвариант 19, §9.3): «берётся при входе в `recording` и отпускается при выходе из `stopping` — в том числе при выходе в `failed`». **Стало:** отпускается при выходе из множества `{recording, stopping}` по любому пути таблицы — строками 12, 13 и **11**. **Что чинится:** оговорка «в том числе при выходе в `failed`» покрывала строку 13 (`stopping → failed`) и не покрывала строку 11 (`recording → failed`, минуя `stopping`); по букве момента отпускания не было вовсе, и Mac оставался не спящим после всякого отказа захвата. **Кого ломает:** К67 написан по множеству, а не по букве, и с v2 совпадает с контрактом дословно — его оговорка «путь строки 11 по букве инварианта не назван» снимается. **Ответы меняются;** из шести мест это единственное, которое пользователь видел бы батареей.

## Определение

### 1. Сессия и её состояние

#### 1.1 Что такое сессия

**Сессия — это одно прохождение машины от заведения до терминального состояния.** Она заводится либо по событию календаря (`origin == .scheduled`), либо по звучащей цели, не отнесённой ни к одному событию (`origin == .adHoc`), и живёт в памяти приложения; между запусками её восстанавливает правило §10, а не хранилище.

```swift
public enum SessionOrigin: String, Codable, Sendable {
    case scheduled   // заведена по событию календаря
    case adHoc       // заведена по сигналу; события нет
}

public struct SessionSnapshot: Codable, Equatable, Sendable {
    public let sessionId: UUID
    public let origin: SessionOrigin
    public let meetingId: UUID?          // MeetingEvent.id (C-001); nil ⟺ origin == .adHoc
    public let state: MeetingStatus      // C-010 §5 — девять значений, второго перечисления нет
    public let recordingId: UUID?        // nil до входа в .recording; дальше не меняется
    public let target: ProcessGroup?     // C-009; звучащая цель, выбранная правилом §5.3
    public let estimate: Double          // 0...1; формула C-009 §1. См. §6: условием перехода не служит
    public let enteredStateAt: Date      // момент входа в текущее состояние
    public let updatedAt: Date
}
```

#### 1.2 Состояние — это `MeetingStatus` C-010, и второго перечисления здесь нет

**Решение:** состоянием сессии объявляется `MeetingStatus` (C-010 §5) — `scheduled`, `armed`, `awaitingSignal`, `recording`, `stopping`, `processing`, `ready`, `failed`, `skipped`.

**Довод.** Эти девять значений уже объявлены и уже применяются **двумя** чужими текстами: C-010 хранит их строкой `meetings.status` и правит методом `setStatus(_:meetingId:)`, а C-016 отдаёт их в UI полем `ActiveSessionView.state`, то есть **уже сегодня называет** `MeetingStatus` **состоянием сессии**. Завести здесь `SessionState` с теми же девятью именами значило бы завести **второе определение одного термина** и обязать себя тотальным отображением между ними — ровно то, от чего §1 C-009 отказался дословно, и ровно тот класс, который проект ловит в своих текстах.

**Цена выбранного названа прямо:** набор состояний машины объявлен **чужим** контрактом. Добавление или снятие состояния есть ломающее изменение и этого контракта, и C-010, и C-016, и делается оно `interface-request`-ом к владельцу `MeetingStatus`, а не решением реализатора машины. **Цена отвергнутого выше:** два перечисления, тотальное отображение между ними и молчаливое расхождение на первой же правке любого из двух.

**Что принадлежит этому контракту, а не C-010:** **переходы**. C-010 объявляет множество значений и хранит одно из них; условий перехода между ними он не называет ни одним словом — проверено чтением §5 и всех его инвариантов целиком. Таблица §7 — единственное место проекта, где эти условия записаны.

**Условие пересмотра названо сразу:** если машине понадобится состояние, которого нет в `MeetingStatus` (сегодня такого нет — см. §8.2 о том, почему «спрашиваем пользователя» состоянием не является), решение принимает владелец `MeetingStatus`, и место этого разбора — запрос к C-010, а не новый тип здесь.

#### 1.3 Тождество сессии и запись

`sessionId` назначается при заведении и не меняется до терминального состояния. `recordingId` — `nil` до входа в `recording`; при входе он назначается машиной, уходит в `CaptureRequest.recordingId` (C-004) и дальше не меняется ни в одном состоянии. Для `origin == .adHoc` `meetingId` равен `nil` на всю жизнь сессии: `MeetingEvent`-а у неё нет, и подставлять его нечем — `RecordingManifest.meetingId` (C-002) и `CaptureRequest.meetingId` (C-004) объявлены опциональными именно под этот случай.

### 2. Вход машины — перечислением, с владельцем у каждого

| Вход | Откуда | Чем приходит |
| -- | -- | -- |
| Сигналы созвона | `ProcessMonitorPort.signals()` (C-009) | `MeetingSignal`; поток начинается со снимка актуального (C-009, инвариант 26) |
| Собственный календарный сигнал | эта машина | `MeetingSignal` с `kind == .calendarWindow`; §5.2 |
| События календаря | `CalendarPort.changes()` и `events(from:to:)` (C-005); строки `meetings` (C-010) | `CalendarChange`, `MeetingEvent` |
| Команды пользователя | фасад C-016 §4 — `startRecording`, `stopRecording`, `skipMeeting` | вызовы методов §3.1 |
| Ответ на спрос | фасад (кнопка уведомления) | `answer(promptId:_:now:)` |
| События захвата | `AudioCapturePort.events()` (C-004) | `CaptureEvent` |
| События очереди | `JobQueue.events()` (C-013) | `JobEvent` |
| События питания | `PowerPort.events()` (C-008) | `PowerEvent` |
| Ход времени | composition root | `tick(now:)`, §4 |
| Настройки | `AppSettings` (C-016 §2) | значения пяти полей, §3.2 |

**Подписка на** `signals()` **— одна на приложение, и это требование, а не совет.** Каждый вызов `signals()` возвращает свой поток, и сигналы между подписчиками не делятся (C-009, инвариант 27), поэтому вторая подписка законна и ничего не ломает у C-009 — **ломает она здесь:** две сессии, считающие оценку каждая по своему потоку, получают снимки на **разные** моменты (инвариант 27 C-009 говорит это дословно), и две сессии, спорящие об одной звучащей цели (§5.4), спорили бы, глядя в два разных мира. Проверяемая форма — инвариант 11.

**Правила разогрева у этой машины нет ни одного, и это прямое следствие инварианта 26 C-009.** До него пустой поток при подписке значил либо «сигналов нет», либо «я только что подписался», и различить их было нечем. Снимок актуального сделал их различимыми: пустой снимок значит, что публикаций не было или они выпали по сроку, — то есть **«сигналов нет» в мире, а не в подписке**. Отсюда §8.3: grace-срок отсчитывается от начала события и подпиской не сдвигается ни на секунду.

### 3. Поверхность

**Поверхность этого контракта — §3.1 и §3.2 вместе.** Сказано здесь потому, что читалось иначе: `SessionCoordinator` со своими типами объявлен §3.1, `Scheduler` и `ScheduledArm` — §3.2, и ссылка «вся поверхность §3.1» теряет второй подраздел целиком ([MEE-289](<https://linear.app/easypto/issue/MEE-289>), Н2 — на этом потерялись два объявления). **Ответов машины это не меняет ни одного:** оба подраздела действуют и действовали.

#### 3.1 `SessionCoordinator`

public protocol SessionCoordinator: Sendable {

    // --- Чтение ---

#### 3.2 `Scheduler`

```swift
/// Что взведено на один будущий созвон. Чистая функция от события, настроек и now.
public struct ScheduledArm: Codable, Equatable, Sendable {
    public let meetingId: UUID
    public let armAt: Date         // startsAt − armLeadSeconds
    public let askAt: Date?        // startsAt − askLeadSeconds; nil при recordingPolicy != .ask
    public let startsAt: Date      // MeetingEvent.start
    public let endsAt: Date        // MeetingEvent.end
    public let graceEndsAt: Date   // startsAt + missingSignalGraceSeconds
}

public protocol Scheduler: Sendable {
    /// События, удовлетворяющие §9.1: isAllDay == false, isCancelled == false, now <= graceEndsAt
    /// и хранимый MeetingStatus нетерминален. Клауза «у встречи нет живой сессии» здесь НЕ
    /// применяется — встреча с живой сессией в плане стоит (§9.1, инвариант 17).
    /// Порядок: по возрастанию armAt; при равенстве — по meetingId.
    func plan(now: Date) async throws -> [ScheduledArm]
    /// Ближайший момент, в который состояние машины обязано измениться; nil — сроков нет.
    func nextDeadline(now: Date) async throws -> Date?
    func start(now: Date) async
    func reschedule(now: Date) async   // календарь изменился, настройки изменились, система проснулась
    func stop() async
}
```

`plan(now:)` **и** `nextDeadline(now:)` **объявлены ради проверяемости, и это сказано вслух.** Без них всякая временная политика проверялась бы только ожиданием: «взвелось ли за две минуты до начала» есть вопрос, на который реальные часы отвечают двумя минутами, а `plan` отвечает сразу и на любом входе. Это та же причина, по которой C-009 объявил инварианты 24—26 проверяемыми «на заданных тестом часах»: проверка сроком в минуту на вектор — не проверка, а ожидание. **Цена названа:** две публичные функции сверх того, что нужно работе машины, и обязанность держать их ответ согласованным с фактическим поведением — инвариант 17.

### 4. Время: параметром, а не часами

**Всякий метод, которому нужен «сейчас», принимает** `now: Date` **параметром.** Часов-порта этот контракт не заводит и синглтона `Date()` внутри машины не допускает.

**Довод — и он не про удобство тестов, а про уже принятую форму проекта:** ровно так время приходит в C-013 (`claimNext(types:excluding:now:leaseSeconds:)`, `JobSubmission.standard(_:runAfter:)`), а карта модулей запрещает `domain-core` синглтоны дословно. Второй способ (порт часов) потребовал бы нового порта, нового фейка и нового контракта на них — при том, что ни один сосед его не просит. **Прогон по восьми контрактам — C-001, C-004, C-005, C-008, C-009, C-010, C-013 и C-016: порта часов не объявляет ни один.** Единственный источник времени, названный проектом, — `DomainTestKit.ManualClock` (C-013, «Фейк для тестов»): **средство теста, а не порт домена**, — и производственная поверхность самого C-013 берёт время параметром `now:`. Два вхождения слова `Clock` в C-004 прочитаны целиком: оба лежат внутри имени поля `fileMinusHostClockBeforeBreakMs` и о часах не говорят (правило 5: счёт вхождений без чтения контекста — не проверка).

**Переходы по сроку.** Машина не имеет собственного таймера: всякий срок наступает внутри `tick(now:)`. Отсюда проверяемая форма обязательства — **инвариант 14**: переход по сроку не наступает раньше срока и наступает не позже первого `tick(now:)` с `now ≥ срок`.

**Граница названа, и она лежит вне зоны этой машины.** Обязанность звать `tick` достаточно часто принадлежит composition root (`app-ui`), а не машине: `nextDeadline(now:)` говорит ему, когда именно, и §8.5 называет верхнюю границу периода. **Ни одной работой CI это обязательство сегодня не проверяется** — проверяется только то, что машина, получив `tick`, исполняет сроки. Сказано прямо, потому что молчаливое исключение означает «не проверяет никто».

### 5. Сигнал, сессия и звучащая цель

#### 5.1 Настройки, которые читает эта машина

**Читает их машина у фасада (**`AppSettings`**, C-016 §2) и ни у кого больше.** Смысл каждого поля назван здесь в проверяемом виде — не вместо комментария C-016, а как правило, которым машина его исполняет.

| Поле | Кто читает | Что значит в этой машине |
| -- | -- | -- |
| `recordingPolicy` | `SessionCoordinator` | `.auto` — переход в `recording` наступает без спроса; `.ask` — наступает после ответа `.record`; `.manual` — наступает только по команде `startRecording` (§8.2) |
| `armLeadSeconds` (120) | `Scheduler` | `armAt == startsAt − armLeadSeconds`: момент перехода `scheduled → armed`, то есть момент, с которого машина обязана наблюдать и вправе записать ранний вход (§8.1) |
| `askLeadSeconds` (30) | `Scheduler`, `SessionCoordinator` | `askAt == startsAt − askLeadSeconds`: момент, в который поднимается спрос `.recordThisMeeting` при `recordingPolicy == .ask`. При других политиках `askAt == nil` и спрос не поднимается (§8.2) |
| `missingSignalGraceSeconds` (900) | `SessionCoordinator` | `graceEndsAt == startsAt + missingSignalGraceSeconds`: момент, в который сессия без звучащей цели уходит в `skipped` (§8.3) |
| `silenceStopSeconds` (300) | `SessionCoordinator` | срок от момента, когда звучащая цель перестала быть актуальной, до перехода `recording → stopping` (§8.4) |

**Соотношения между значениями этот контракт не требует ни одного, и это решение.** `missingSignalGraceSeconds` меньше `signalTtlSeconds` (C-009 §5) — законная настройка, и машина при ней ведёт себя по правилам §8.3 без оговорок: снимок при подписке (C-009, инвариант 26) снял тот единственный вход, на котором такое соотношение давало ложный `skipped`. **До v9 соотношение было существенным** — это записано в отчёте по [MEE-272](<https://linear.app/easypto/issue/MEE-272>) как цена отвергнутого исхода (б); сегодня оно безразлично, и сказано это здесь, чтобы прежний довод не перенесли в критерии.

**Значения в скобках — умолчания C-016 (**`AppSettings.slice1Defaults`**), а не константы этого контракта.** Машина не имеет права зашивать ни одно из пяти: правило §7 и §8 записаны через имена полей.

#### 5.2 Собственный календарный сигнал

**Машина — та самая «сторона, публикующая календарный сигнал», о которой говорят шапка раздела «Инварианты» C-009 и его инварианты 11, 12 и 17.** C-009 прямо оставил этому контракту вопрос, как этот сигнал доходит до своего потребителя (инвариант 26, последний абзац). Ответ:

**Календарный сигнал не ходит потоком: он строится в момент пересчёта оценки и потребляется той же сессией, которая его построила.** Для сессии с `origin == .scheduled` и событием `e` в момент `now`:

* сигнал существует тогда и только тогда, когда `e.start ≤ now < e.end`;
* `kind == .calendarWindow`, `pid == nil`, `bundleId == nil`, `group == nil`, `provider == nil`, `meetingId == e.id`, `weight == weights.calendarWindow` таблицы C-009 §5, `observedAt == now`.

**Чем исполняется инвариант 24 C-009.** Разрыв по `observedAt` между двумя построениями одной пары «вид + источник» равен периоду пересчёта, а пересчёт наступает в каждом `tick(now:)`; верхняя граница периода `tick` названа в §8.5 и меньше `signalTtlSeconds`. Отдельного вида, флага «подтверждение» и второго способа публикации этот контракт не заводит — ровно как того требует инвариант 24.

**Откуда машина берёт** `weights.calendarWindow` **и** `signalTtlSeconds`**:** от публичного члена `domain-core`, отдающего прочитанные значения таблицы весов (C-009 §6). Файла машина не читает, пути к нему не знает и своего декодера не заводит.

**Цена решения названа прямо:** календарный сигнал не виден никому, кроме своей сессии, — ни другой сессии, ни UI, ни тестам чужого модуля. **Условие пересмотра:** если у этого сигнала появится второй потребитель, вырожденная доставка перестаёт годиться, и это издание **этого** контракта, а не решение реализатора. **Отвергнуто:** публиковать календарный сигнал через собственный поток-шину домена — конструкция без сегодняшнего сценария, требующая своего правила подтверждения, своего фейка и своих критериев; проект уже платил за конструкцию без сценария (C-009, два пути чтения таблиц, IR-027).

#### 5.3 Звучащая цель

**Определение.** Звучащая цель сессии в момент `now` — актуальный (C-009 §1, инвариант 25) сигнал с `kind == .clientAudioOutput` и `group != nil`, отнесённый к этой сессии правилом §5.4.

**Отнесение есть условие необходимое и не достаточное, и указатель на единственное исключение стоит здесь, а не только у самого исключения.** §5.4 последним абзацем говорит: **оспариваемый сигнал остаётся отнесённым** к каждой из спорящих сторон — и **целью не является ни у одной**, пока спор не разрешён. Читатель, дошедший до лестницы ниже, обязан снять таких кандидатов **прежде** неё: лестница выбирает одну цель из нескольких и об исключении не знает. **Указатель напечатан потому, что ссылка «правилом §5.4» формально его покрывает, а читатель, получивший готовый ответ лестницей, в §5.4 уже не идёт** — ровно тот механизм, который §8 правил проекта разбирает на базовой и действующей редакциях: нашедший первое останавливается на нём, потому что не знает о втором.

Если таких сигналов несколько, цель одна и выбирается так:

1. если у сессии есть событие с `conference?.provider != nil` — сигналы, у которых `provider` равен ему, сильнее прочих;
2. среди оставшихся — больший `observedAt`;
3. при равенстве — лексикографически меньший `group.appKey`.

Правило тотально и детерминировано: третья ступень различает любые два сигнала, потому что двух актуальных сигналов одной пары «вид + источник» по инварианту 25 C-009 не бывает, а пара для сигнала с группой есть её `appKey`.

**Почему цель определена через** `clientAudioOutput`**, а не через «есть хоть какой-нибудь сигнал».** Две причины, и обе проверяемые. **Первая:** записывать нужно **группу**, а `group != nil` обещан только видам `clientRunning` и `clientAudioOutput` (C-009, инвариант 17); `microphoneInUse` группы может не иметь вовсе, и `CaptureRequest.group` из него не строится. **Вторая:** `clientRunning` означает «процесс клиента запущен», а не «созвон идёт» — запущенный и молчащий клиент есть штатный вход, названный поимённо в §«Фейк для тестов» C-009.

**И названа мера, которой этот выбор безопасен.** `clientAudioOutput` **не** означает «слышен звук»: измерено (C-009, §«Что вне контракта»), что флаг держится у процесса, который открыл вывод и пишет цифровую тишину. Значит цель появляется в момент, когда клиент **открыл вывод**, то есть при входе в созвон, а не при первом произнесённом слове, — и созвон, где все молчат, машина не пропускает. Без этого замера правило §8.3 («нет цели 15 минут → `skipped`») было бы опасным.

#### 5.4 Отнесение сигнала к сессии

Сигнал `s` относится к сессии `S` в момент `now` **по первому подошедшему правилу, и правило читается для пары «сигнал — сессия», а не для сигнала вообще:** один и тот же сигнал бывает отнесён к нескольким сессиям сразу, и это не сбой, а спор (абзац ниже). **Номера правил 1—4 не сдвинуты ни один, и новое правило обозначено буквой** по тому же доводу, по какому обозначены буквами строки 1а и 1б §7: на номерах стоят чужие критерии (К24, К25), и сдвиг сломал бы их молча.

**Правило 1.** `s.kind == .calendarWindow` → относится к сессии со `S.meetingId == s.meetingId` и ни к какой другой.

**Правило 1а** *(издание v6)*. `S.origin == .adHoc`, `S` не терминальна, и `s` есть тот самый сигнал, по которому `S` заведена (§8.6): `s.group?.appKey` равен `appKey` цели, назначенному при заведении → относится к `S`. **Прочих сессий это правило не касается ни одной, и правил 2 и 3 оно не отменяет:** сигнал, отнесённый к ad-hoc-сессии правилом 1а, **остаётся отнесённым** и к сессии события, если её условие истинно, — иначе занятость цели §7.1 и спор ниже перестали бы читаться. **Спор ad-hoc-сессии не касается:** сторонами спора являются сессии, к которым сигнал отнесён правилом **3**, а ad-hoc-сессия в их число не входит — её отнесение даёт правило 1а, стоящее раньше.

**Правило 2.** `s.provider != nil` и у `S` есть событие с `conference?.provider == s.provider`, и `armAt ≤ now ≤ graceEndsAt` либо `S.state ∈ {recording, stopping}` → относится к `S`.

**Правило 3.** `s.provider == nil` (браузер или провайдер не определён) и `armAt ≤ now ≤ graceEndsAt` либо `S.state ∈ {recording, stopping}` → относится к `S`.

**Правило 4.** Иначе не относится ни к одной сессии.

**Чего не было до v6 и чем это стоило, сказано здесь, а не выведено читателем.** Правил было четыре, и **ни одно из них не относило сигнал к ad-hoc-сессии ни в одном её состоянии:** правило 2 требует у сессии события, которого у ad-hoc нет по определению (§1.3); правило 3 требует `s.provider == nil`, то есть покрывает браузер и не покрывает настольного клиента, а незапланированный созвон в настольном клиенте и есть главный вход §8.6; оба сверх того требуют окна `armAt ≤ now ≤ graceEndsAt`, которого у сессии без события нет. **Отсюда прямо, и всё это читается на самом тексте v5:** у ad-hoc-сессии не было звучащей цели (§5.3 определяет цель через отнесение), `SessionSnapshot.target` был `nil` во всех состояниях, `estimate` (§6) был нулевым, §7.1 и инвариант 13 сравнивали `nil` с `nil`, а срок §8.4 отсчитывался «с момента, в который звучащая цель перестала быть актуальной» — от момента, которого не наступало. Правило 1а закрывает всё перечисленное одной клаузой.

**Сигнал, не отнесённый ни к одной сессии правилами выше и удовлетворяющий прочим условиям §5.3 — актуальный,** `kind == .clientAudioOutput`**,** `group != nil`**, — есть вход ad-hoc** (§8.6). **Сказано это так, а не «звучащая цель, не отнесённая ни к одной сессии», и разница не словесная:** звучащая цель по §5.3 есть цель **сессии**, и сигнал, не отнесённый ни к одной, целью не является ни у кого — то есть прежняя формулировка называла пустое множество и по букве не срабатывала ни разу. **И второе следствие той же правки:** заведённая по такому сигналу ad-hoc-сессия получает его своей целью правилом 1а, и тот же сигнал входом ad-hoc **больше не является** — потому §8.6 и не поднимает по нему второго спроса.

**Сигнал, отнесённый сразу к нескольким сессиям — правилом 2 либо правилом 3, безразлично каким, — есть спор, а не выбор.** Это в точности случай «две встречи одновременно» из `architecture.md` §3.2. **Признак спора есть ЧИСЛО сессий, к которым сигнал отнесён, а не номер отнёсшего правила, и это правка издания v7.** Прежняя редакция называла спором отнесение **правилом 3** и разрешала его тем, что «правило 2 отнесло цель ровно к одной сессии», — а правила 2 и 3 взаимно исключаются по `s.provider` (2 требует `!= nil`, 3 требует `== nil`), то есть для сигнала, отнесённого правилом 3, правило 2 не относило его **ни к кому и никогда**: названная ветвь разрешения была мертва, а случай, который абзац о цене ниже называет спором прямо — два пересекающихся созвона одного провайдера, отнесённых правилом 2 к обеим сессиям, — не попадал под определение вовсе и не получал ни спроса, ни правила. **Отнесение ровно к одной сессии спором не является** — тогда цель её и только её, и спрос не поднимается. **Отнесение к двум и более:** поднимается **один** спрос `.whichMeeting(candidates:)` на спор, `candidates` — `sessionId` кандидатов по возрастанию, и **до ответа не записывает ни одна**. Нет ответа — каждая сессия уходит в `skipped` по своему `graceEndsAt`.

**Оспариваемая цель не является звучащей целью (§5.3) ни для одной из сторон, пока спор не разрешён, и это чтение названо прямо, потому что при другом абзац выше спорит с таблицей §7.** Отнесения правилом 3 это не отменяет: сигнал остаётся отнесённым к каждой из сторон и входит в её `estimate` (§6) — не является он **целью**. Отсюда обе половины абзаца выше исполняются строками таблицы, а не помимо них: строки 6, 8 и 16 не срабатывают ни у одной стороны, потому что звучащей цели нет, — это и есть «до ответа не записывает ни одна»; а в момент `graceEndsAt` каждая уходит в `skipped` строкой 9 по своему сроку. **Спор кончается ровно двумя способами, и третьего нет** (счёт правится изданием v7 вместе с определением выше, потому что прежний называл первым способом ту самую мёртвую ветвь): **(1)** пришёл ответ на спрос `.whichMeeting(candidates:)` — цель становится целью названной сессии и не является целью прочих кандидатов; **(2)** сигнал перестал быть отнесённым больше чем к одной сессии — он выпал по сроку (C-009, инвариант 25), либо сторона стала терминальной, либо её окно `armAt ≤ now ≤ graceEndsAt` закрылось. **Во втором случае спрос снимается машиной** (`SessionChange.promptWithdrawn`), а цель, если отнесённой осталась ровно одна сессия, становится её звучащей целью со всеми последствиями строк 6 и 8. **Названо это здесь потому, что молчание читалось бы как «спрос висит до ответа или до конца жизни всех сторон», а §3.1 объявляет** `promptWithdrawn` **и правила снятия для** `.whichMeeting` **не давал ни один раздел.** **Цена выбранного:** сторона, которая записывала бы, не будь спора, теряет начало созвона, пока человек не ответил, а при молчании — запись целиком. **Цена отвергнутого чтения** («цель есть у обеих») **выше, и она не гипотетическая, а читается на самом тексте:** оно требует от каждой стороны разом записывать (строки 6 и 8 истинны) и не записывать («до ответа не записывает ни одна»), а в `graceEndsAt` — уйти в `skipped` по абзацу выше и не уйти по строке 9.

**Цена названа:** пересекающиеся встречи у одного провайдера (два подряд Zoom-созвона с наложением) спрашивают пользователя всегда, потому что правило 2 отнесёт цель к обеим. **Отвергнуто — разводить их по** `JoinInfo.meetingId`**:** C-009 прямо говорит, что порт не различает, какой именно созвон идёт, и что `meetingId` из ссылки со структурным полем не сверяется; правило, стоящее на несверенном значении, даёт ответ, но молча.

### 6. Оценка `estimate`: считается, отдаётся и **не** служит условием ни одного перехода

**Как считается.** По формуле C-009 §1 — `estimate = 1 − Π (1 − weight_i)` — над множеством сигналов, отнесённых к сессии по §5.4 и актуальных по инварианту 25 C-009, включая собственный календарный сигнал §5.2. Своего определения актуальности, своего срока и своей формулы у этого контракта нет.

**Где применяется: нигде в переходах. Сказано прямо, потому что читатель ждёт обратного** — C-009 §1 оставил этому контракту «порог, при котором `SessionCoordinator` переходит в `Recording`», и постановка [MEE-205](<https://linear.app/easypto/issue/MEE-205>) называет оценку входом машины.

**Довод — арифметический, а не вкусовой, и он проверяется прогоном на сегодняшней таблице весов (C-009 §5).** Слияние идёт по **парам** «вид + источник», то есть каждый новый запущенный клиент входит в произведение отдельным множителем. Пусть ни одного сигнала `clientAudioOutput` нет вовсе — то есть ни одна цель захвата не названа:

| Вход | `estimate` |
| -- | -- |
| окно события | 0,2 |
| окно + 1 запущенный клиент | 0,52 |
| окно + 1 клиент + микрофон | 0,712 |
| окно + 3 клиента + микрофон | 1 − 0,8·0,6⁴ = **0,89632** |
| окно + 5 клиентов | 1 − 0,8·0,6⁵ = **0,937…** |
| окно + N клиентов, N → ∞ | → 1 |

**Отсюда прямо: любой порог, кроме единицы, берётся достаточным числом запущенных и молчащих клиентов, и ни один из этих входов не называет, что записывать.** Порог `estimate ≥ 0,8` красен на входе «пять запущенных клиентов в окне события» — записи не из чего собрать (`CaptureRequest.group` неоткуда взять), а условие выполнено. Порог, который нельзя исполнить на входе, где он истинен, — не порог.

**Что взято вместо порога:** предикат по составу — звучащая цель §5.3. Он отвечает сразу на оба вопроса, «записывать ли» и «что записывать», одним значением, и второго значения для второго вопроса не требует.

**Цена выбранного названа честно.** Поле `SessionSnapshot.estimate` вычисляется и **не имеет сегодня ни одного применяющего** — это ровно тот класс, который C-009 §6 назвал у себя («значение, у которого есть читатель, но нет применяющего»), и я называю его у себя, а не прячу. Поле оставлено по двум причинам: формулу слияния C-009 обязывает исполнять **потребителя**, и место, где она исполняется, обязано быть одно; а наружу, к человеку, оценка пойдёт изданием C-016, которого это издание не касается ни символом. **Условие снятия поля:** если C-016 откажется её показывать и второго применяющего не появится, поле снимается изданием этого контракта.

**Отвергнуто ещё два исхода, и оба с ценой.** (а) Завести порог настройкой `AppSettings` — это правка C-016, то есть чужого контракта, а сверх того порог, заданный числом, остаётся ложным по доводу выше при любом значении. (б) Взять порогом `weights.clientAudioOutput` из таблицы C-009 — тогда порог поедет за весом: уронив вес звука до 0,5, таблица молча разрешила бы запись по паре «окно + запущенный клиент» (0,52), и правило поведения менялось бы правкой данных.

### 7. Переходы — таблица полная, иных переходов нет

Условия читаются в момент `tick(now:)` — **и, сверх него, в момент вызова команды §3.1: команда исполняется немедленно, а всякий иной вход §2 до ближайшего** `tick` **состояния не меняет** («Поведение»). **Сказано так, а не «в момент прихода названного входа», и разница не словесная:** команды §2 называет входами наравне с `CaptureEvent`, `JobEvent`, `PowerEvent`, сигналами и `CalendarChange`, — и прежняя редакция отдавала строку 11 (`CaptureEvent.failed`) и строку 12 (`CaptureEvent.stopped`) моменту события, тогда как «Поведение» отдаёт их ближайшему `tick`. Два места давали два ответа на вопрос «когда меняется состояние», и различал их потребитель `changes()`, читающий поток между событием и `tick`. Строки проверяются **в порядке таблицы**: первое подошедшее условие побеждает.

**Восстановительное заведение сессии (§10, перечень А) этой таблицей не описывается, и это сказано здесь, а не выведено читателем.** Оно происходит **только** в `start(now:)`, ровно один раз за запуск приложения, и ни одним `tick` не повторяется; счёт его способов закрыт — их **два**, оба в §10 перечне А (вход в `processing` и вход в `failed`), и третьего нет. **Именно поэтому оно не внесено строками сюда:** строка таблицы читается в каждый `tick`, и заведения §10, став строками, звали бы `recover(directory:)` на одной и той же записи при каждом `tick`. Разбор обоих способов и цена каждого — §«Ломающие изменения против v3», п. 1.

**Строки 1а, 1б и 1в обозначены буквами, а не номерами, и это решение с названной ценой.** Номера 2—16 стоят построчно в 88 критериях перечня [MEE-277](<https://linear.app/easypto/issue/MEE-277>) — К29—К44, — и сдвиг номеров сломал бы их **молча**: критерий «строка 11» указал бы на другой переход, а перечень остался бы зелёным по построению (правило 7 проекта). **Цена выбранного:** в таблице **три** обозначения с буквами, и счёт строк, бывший «шестнадцать» до v2 и «восемнадцать» до v6, стал **девятнадцать** — 1, 1а, 1б, 1в, 2…16. **Число правится изданием v7, а не абзацем ломающих изменений, потому что оно стоит здесь живым временем:** строку 1в завело издание v6, первую половину этого же предложения оно поправило («строки 1а, 1б **и 1в**»), а вторую — цену — не тронуло, и §7 с той минуты отвечал на вопрос «сколько строк в таблице» **двумя** способами: «девятнадцать» абзацем ниже и в §«Ломающие изменения против v5», «восемнадцать» здесь. **К46 стоит на девятнадцати**, и это третий раз, когда данное число оказалось ложным, — но впервые в контракте, а не в перечне. **Цена отвергнутого:** пятнадцать чужих ссылок, съехавших на одну строку, и ни одного признака, которым это ловится.

**Три заводящие по событию строки взаимно исключают друг друга по** `now`**,** и порядок между ними безразличен: `now < armAt`, `armAt ≤ now < e.start` и `e.start ≤ now ≤ graceEndsAt` есть разбиение отрезка, а не перечень предпочтений. **Со строками 1в и 16 они не пересекаются ни при каком входе:** у сессии события есть `meetingId`, у ad-hoc его нет (инвариант 4), и условия заведения у них разные — §9.1 против §8.6. Порядок таблицы существен там, где условия пересекаются.

**Асимметрия знаков —** `>` **в строке 3 и** `≥` **в строке 9 по одному и тому же** `graceEndsAt` **— намеренна, и довод напечатан здесь, чтобы её не «выровняли» молча.** Момент `graceEndsAt` **принадлежит** сессии: §9.1 заводит её при `now ≤ graceEndsAt`, а §8.3 требует, чтобы решение принималось **в** названные пятнадцать минут, а не после них. Отсюда: строка 9 срабатывает **в сам момент** `graceEndsAt` (`≥`) — это и есть решение по grace, принятое в срок; строка 3 срабатывает **строго после** (`>`) — это конец жизни сессии, у которой момента решения не было вовсе. Разные субъекты — разные знаки. **Верхняя граница строки 2 (**`now ≤ graceEndsAt`**) заведена тем же доводом:** без неё третья клауза строки 3 не срабатывала бы ни разу, потому что строка 2 стоит раньше и истинна на всём `now ≥ armAt`, — и обещание §9.2 не исполнялось бы ни одной верной реализацией. **Граница этого утверждения названа вместе с ним, потому что молчание о ней читалось бы как её отсутствие:** оно верно тогда и только тогда, когда `armAt ≤ graceEndsAt`, то есть когда `armLeadSeconds + missingSignalGraceSeconds ≥ 0`. **Соотношений между настройками этот контракт не требует ни одного (§5.1)**, и потому клауза была мертва не тождественно, а на всяком наборе с неотрицательными сроками, включая умолчания C-016. Верхняя граница строки 2 снимает эту зависимость от знака настроек целиком: строка 2 и третья клауза строки 3 теперь не пересекаются ни при каких значениях.

**Клауза строки 9 названа перечнем причин, а не одной, и довод в том, что причин у неё три.** Строка 8 требует трёх вещей разом — звучащая цель есть, цель не занята (§7.1), запись разрешена политикой (§8.2), — и её отрицание у живой сессии в момент `graceEndsAt` даёт ровно три случая: цели нет; цель есть и занята чужой записью; цель есть и политика её не отдала (`.manual`; `.ask`, на который не ответили). **Прежняя редакция называла только первый, и два других повисали:** §8.2 обещал `.ask` без ответа «живёт до `graceEndsAt` и уходит в `skipped`», §8.3 обещал терминальность «третьего исхода нет», а таблица не давала ни одной строки, которой сессия со звучащей целью могла бы уйти, — она оставалась в `awaitingSignal` навсегда. **Спор §5.4 четвёртым случаем в перечень не входит намеренно:** оспариваемая цель звучащей целью не является, и он закрыт первым случаем. **Отвергнута короткая форма «либо** `now ≥ graceEndsAt`**» без перечисления:** в полной машине она даёт тот же ответ, потому что строка 8 стоит раньше и побеждает всюду, где запись начать можно, — но читается как отмена строки 8, а цена молчаливого «выравнивания» двух мест по одному и тому же `graceEndsAt` этим контрактом уже названа абзацем выше. **Цена выбранного:** клауза длиннее и ссылается на три раздела. **Цена отвергнутого:** реализатор, прочитавший строку 9 прежде строки 8, пишет машину, которая в `graceEndsAt` не записывает никогда.

**Терминальные состояния —** `ready`**,** `failed`**,** `skipped`**; исходящих переходов у них нет ни одного.** Вход, пришедший в терминальном состоянии, состояния не меняет; команда, адресованная терминальной сессии, бросает `sessionIsTerminal`. **Довод:** встреча, вернувшаяся из `ready` в `recording`, сделала бы ложной каждую строку хранилища, которая на ней стоит; повторная обработка заводит новую работу очереди, а не оживляет сессию (§8.7).

#### 7.1 Одна группа — одна запись

**Цель, занятая идущей записью, не отдаётся второй сессии.** Строки 6, 8 и 16 не срабатывают, если существует сессия в состоянии `recording` или `stopping` с `target?.appKey`, равным `appKey` цели. Команда `startRecording`, упёршаяся в это, бросает `alreadyRecording(sessionId:)`.

**Довод — замер, а не осторожность:** один `appKey` в захвате есть один tap, и C-009 прямо запрещает предполагать, что «один PID или одна группа — один созвон». Два tap-а на одну группу дали бы две записи одного звука и два манифеста, спорящих о том, что записано.

### 8. Политики `architecture.md` §3.2, приведённые к проверяемому виду

**Каждый пункт ниже назван строкой §3.2, и рядом сказано, чем он стал.** Это и есть работа этого контракта: текст §3.2 хранит **решения** (§10 правил) и инвариантов нести не может.

#### 8.1 «Взводит боевую готовность за T−2 мин»

**Стало:** `scheduled → armed` в момент `armAt == e.start − armLeadSeconds` (строка 2). С этого момента сессия наблюдает вход §2, считает оценку и **вправе записать**: строка 6 разрешает `armed → recording` до начала события. **Довод:** участники входят в созвон раньше начала чаще, чем позже, а два минутных запаса — это и есть то, ради чего взведение существует; запретив ранний вход, машина пропустила бы первые минуты по правилу, а не по недосмотру. **Число «2 мин» из §3.2 не переносится:** оно живёт в `AppSettings.armLeadSeconds`.

#### 8.2 «Автозапуск против „спросить"»

**Стало — три правила по** `recordingPolicy`**, и ни одно не спрашивает о правах. Субъект у всех трёх один и назван прежде них, а не оставлен читателю: сессия с событием (**`origin == .scheduled`**). Что политика значит для ad-hoc-сессии, сказано пунктом ниже и сказано ИНАЧЕ; всякая из трёх клауз, прочитанная как правило машины, спорит с §8.6.**

* `.auto` — строки 6 и 8 срабатывают, как только есть звучащая цель. Спрос по такой сессии не поднимается ни разу;
* `.ask` — в момент `askAt` поднимается спрос `.recordThisMeeting`; **у сессии, заведённой строкой 1а или 1б при уже прошедшем** `askAt`**, спрос поднимается в момент заведения** — срок не «догоняется» и не пропускается. Строки 6 и 8 срабатывают только после ответа `.record`. Ответ `.skip` уводит сессию в `skipped` (строки 4, 9). Нет ответа — сессия живёт до `graceEndsAt` и уходит в `skipped` строкой 9;
* `.manual` — спрос по такой сессии не поднимается ни разу. **Политика не отдаёт цель сама: сколько бы ни было звучащих целей и сколько бы ни пришло** `tick`**-ов, строки 6 и 8 по ним не срабатывают.** Отдаёт цель **команда** `startRecording(meetingId:)` — и с момента её вызова третья клауза строк 6 и 8 («запись разрешена политикой») истинна, сессия уходит в `recording` **строкой 6 либо 8**, ровно тем же способом, каким при `.ask` её уводит ответ `.record`. **Прежняя редакция говорила здесь «строки 6 и 8 не срабатывают никогда» и той же скобкой — «команда даёт цель, и та уходит строкой 6 либо 8»: два ответа на один вход в одном предложении.** Цена прежней редакции названа, потому что она не бумажная: при чтении «никогда» буквально у команды не остаётся **ни одной** строки таблицы, инвариант 2 запрещает переход помимо неё, а §3.1 обязывает `startRecording` вернуть `recordingId` — то есть эта половина неисполнима ни одной верной реализацией, и всякая работающая машина исполняет скобку, но помимо таблицы. **Ad-hoc-сессию при** `.manual` **заводит сразу в** `recording` **строка 16** (§8.6).

**Для ad-hoc-сессии (§8.6) «запись разрешена политикой» читается иначе, и это сказано пунктом, потому что молчание читалось бы как «как у всех».** Цель отдаётся ad-hoc-сессии **только** ответом `.record` на её спрос либо командой `startRecording(meetingId: nil)` — **при** `.auto` **тоже**, и довод тот же, которым §8.6 требует спроса при `.auto`: согласие записывать **запланированное** не есть согласие записывать незапланированное. **Отсюда строка 8 у ad-hoc-сессии не срабатывает ни при какой политике раньше ответа либо команды**, хотя звучащая цель у неё есть с самого заведения (§5.4, правило 1а). **Без этого пункта правило 1а дало бы при** `.auto` **немедленную запись строкой 8 — то есть отменило бы обещание §8.6 молча**, и это ровно та цена, ради которой пункт напечатан.

**«Спрашиваем пользователя» состоянием машины не является, и это решение.** Спрос — **выход** машины (`SessionPrompt`), а не состояние: сессия при поднятом спросе стоит в `armed` либо `awaitingSignal` и продолжает считать сроки. **Довод:** заводить десятое состояние значило бы править `MeetingStatus`, то есть чужой контракт и хранимую колонку, ради значения, которое не переживает перезапуск приложения; ответ на спрос не хранится и после перезапуска спрашивается заново (§10). **Цена названа:** снимок сессии не говорит, висит ли спрос, — это отдельный ответ `prompts()` и отдельное событие `promptRaised`.

**Чем спрос доходит до человека — не предмет этого контракта.** Машина поднимает его и снимает; показывает его уведомлением, пунктом меню или окном — фасад и UI (C-016). **Отсюда прямо: машина не читает снимок прав и не меняет поведения от того, выдано ли право на уведомления.** Обязательность `.notifications` при `recordingPolicy == .ask` — правило C-016 (инвариант 25), и исполняет его мастер прав, а не машина.

#### 8.3 «Grace-период на опоздание: сигнала нет 15 мин после начала → `Skipped`»

**Стало:** строка 9 — `awaitingSignal → skipped` в момент `graceEndsAt == e.start + missingSignalGraceSeconds`, если к этому моменту запись не начата. **Случаев ровно три, и это тот же счёт, каким их называет §7, — прежняя редакция давала четыре:** **звучащей цели нет** — случай, ради которого этот подраздел и написан; либо цель есть, а строка 8 по ней не сработала — **цель занята** (§7.1) либо **политика её не отдала** (§8.2). **Спор §5.4 четвёртым случаем не является и закрыт первым:** оспариваемая цель звучащей целью не является ни для одной стороны, и потому у стороны спора цели **нет**. **Прежняя редакция ставила его третьим подслучаем «цель есть» и в той же скобке говорила о нём «звучащей целью не является» — то есть относила один и тот же вход к обоим случаям разом, а §7 относит его к первому.**

**«Сигнала нет» значит «нет звучащей цели» (§5.3), и это ответ на прямой вопрос постановки.** Выбрано из двух законных чтений:

* **взято:** «нет звучащей цели» — то есть ложен ровно тот предикат, который и начал бы запись;
* **отвергнуто:** «пуст набор актуальных сигналов сессии» — читается ближе к букве §3.2, но оставляет машину без завершения: запущенный и молчащий клиент держит набор непустым, и сессия висела бы в `awaitingSignal` неограниченно. Чинить это пришлось бы **вторым** сроком, которого нет ни в §3.2, ни в `AppSettings`.

**Довод за взятое — три части.** Одно определение работает в двух местах (начало записи и grace), а не два расходящихся. Машина терминальна по построению: в момент `graceEndsAt` сессия либо уже в `recording`, либо уходит в `skipped`, третьего исхода нет. И §3.2 читается дословно: решение принимается в названные пятнадцать минут, а не позже.

**«Третьего исхода нет» стало утверждением о таблице, а не обещанием о ней, и это правка издания v5.** До него третий исход существовал: сессия, у которой цель есть, а строка 8 по ней не сработала, не подходила ни под одну строку таблицы. **Теперь третьего исхода нет по построению, и построение названо:** строка 8 стоит в таблице раньше строки 9 и побеждает всюду, где запись начать можно; всюду, где нельзя, срабатывает строка 9. Проверяется перебором трёх политик на двух состояниях цели (свободна, занята чужой записью) в момент `graceEndsAt`. **Выбор чтения, разобранный выше, от этой правки не зависит ни на сколько:** он решает, чем «сигнала нет» является, а правка решает, что бывает, когда сигнал есть, а записать по нему нельзя.

**Цена взятого названа, и она измерена, а не предположена:** «клиент запущен, но молчит» уйдёт в `skipped`. Опасно это было бы, если бы `clientAudioOutput` означал слышимый звук, — но он означает **открытый вывод** и держится при цифровой тишине (C-009, §«Что вне контракта», замер [MEE-8](<https://linear.app/easypto/issue/MEE-8>) R1). Созвон, в котором все молчат, цель даёт; клиент, запущенный без созвона, — нет. **Условие пересмотра:** замер, показывающий, что у какого-то клиента вывод открывается не при входе в созвон, а позже, переводит это правило в `interface-request` к C-009 и в издание этого контракта.

**Снимок при подписке (C-009, инвариант 26) в этом правиле участвует ровно одним следствием, и оно названо:** подписка не молодит сигналы и срок не сдвигает. Сессия, заведённая посреди идущего созвона (приложение запустили в середине встречи), получает при подписке снимок актуального и находит цель **сразу**, а не через `signalTtlSeconds`; поэтому `graceEndsAt` считается от `e.start` и от подписки не зависит ни на секунду.

#### 8.4 «Критерии остановки» и «встреча, ушедшая за расписание»

**Стало — четыре правила, и первое отвечает на обе строки §3.2 сразу:**

1. **Конец окна события сам по себе запись не останавливает.** Это и есть «продолжаем, пока есть звук» в проверяемом виде: `e.end` не стоит ни в одном условии строки 10.
2. `recording → stopping`**, когда прошло** `silenceStopSeconds` **с момента, в который звучащая цель перестала быть актуальной** и не появилась снова. Момент отсчёта — `observedAt` последней актуальной цели плюс `signalTtlSeconds` (момент, в который она выпала из слияния по C-009 §1), а не момент, когда машина это заметила.
3. **Команда** `stopRecording` — немедленно, в любом из состояний `recording`.
4. `CaptureEvent.failed` — не остановка, а `failed` (строка 11): манифест в этом случае не обещан.

**Один срок на оба случая §3.2 («N минут после конца события» и «M минут во время») — решение, и довод механический:** настройка в `AppSettings` **одна** — `silenceStopSeconds`, — и второй срок потребовал бы правки C-016, то есть чужого контракта, ради различения, которого ни один замер не обосновывает. **Цена названа:** созвон, замолчавший на шесть минут в середине (все вышли и вернулись), будет остановлен и продолжен второй записью; при сегодняшнем умолчании в 300 с это пять минут закрытого вывода, а не пять минут тишины в комнате.

`CaptureEvent.systemSilent` **(C-004) условием остановки не является ни при каких значениях — и это сказано пунктом, а не умолчанием.** C-004 говорит о тишине **в треке**, а не о закрытом выводе, и сам называет пару «тишина в тапе при открытом выводе» подсказкой о неверной группе или неданном праве, которую складывает домен. **Машина эту пару складывает и не останавливает по ней запись:** остановка по тишине в тапе выключила бы запись созвона, где говорит только пользователь (микрофон пишется, система молчит). Что делать с подсказкой дальше — показывать ли её человеку — сегодня не закрыто ничем: `AppErrorView` такого кода не несёт, и это названо строкой в отчёте, а не решено здесь.

#### 8.5 Верхняя граница периода `tick`

`tick(now:)` **приходит не реже чем раз в** `signalTtlSeconds` **минус запас реализации, и не позже ближайшего** `nextDeadline(now:)`**.** Первая половина — то, чем исполняется инвариант 24 C-009 для календарного сигнала (§5.2): разрыв между двумя построениями обязан быть **меньше** срока, а не равен ему. Вторая половина — то, чем исполняется инвариант 14: срок наступает не позже первого `tick` после него.

**Запас контракт не называет числом** — ровно по доводу инварианта 24 C-009: названо, что разрыв меньше, а не равен, а с каким запасом реализация в это укладывается, её выбор. **Обязанность лежит на composition root, и CI её не проверяет** (§4, граница).

#### 8.6 «Ad-hoc созвон без события — отдельный вход в ту же машину»

**Стало:** сигнал, не отнесённый ни к одной сессии и удовлетворяющий прочим условиям §5.3 (§5.4, правило 4), **заводит ad-hoc-сессию** — `origin == .adHoc`, `meetingId == nil`, целью назначен этот сигнал (§5.4, правило 1а).

**Условие заведения одно на обе заводящие строки и напечатано здесь, ровно как условие заведения по событию напечатано в §9.1, а строки 1в и 16 §7 стоят на нём дословно:** такой сигнал есть **и** живой ad-hoc-сессии с этим `appKey` нет (инвариант 4). **Состояние заведения есть функция от того, ЧЕМ заведение пришло, а политика решает только внутри первой из двух ветвей, и это правка издания v7** — прежняя редакция говорила «функция от политики», а у второй ветви клаузы политики нет ни одной. **Ветвь первая —** `tick`**:** сигнал прочитан ходом времени, и тогда при `recordingPolicy != .manual` сессия заводится в `awaitingSignal` **строкой 1в** и поднимает спрос `.recordThisMeeting` со своим `sessionId` и `expiresAt == nil`, а при `.manual` не заводится вовсе. **Ветвь вторая — команда** `startRecording(meetingId: nil)`**:** сессия заводится сразу в `recording` **строкой 16**, **при любом значении** `recordingPolicy`**, включая** `.auto` **и** `.ask`, и спроса не поднимается — команда есть то самое решение человека, ради которого спрос и существует. **Две ветви не спорят, потому что читаются в разные моменты** (§7): строка 1в — в `tick`, строка 16 — в момент вызова команды; а заведение, случившееся первым, делает условие ложным для второго. Иных способов завести ad-hoc-сессию нет ни одного, и отсутствие третьего проверяется перебором (инвариант 2).

**Ответ** `.record` **уводит сессию в** `recording` **строкой 8** — до ответа строка 8 не срабатывает ни при какой политике, потому что цель ad-hoc-сессии отдаёт не политика, а ответ либо команда (§8.2). **Ответ** `.skip` **уводит её в** `skipped` **строкой 9.** **Спрос снимается сам, когда цель перестала быть актуальной**, и сессия уходит в `skipped` **той же строкой 9, клаузой, названной для ad-hoc поимённо**: спрашивать про созвон, который уже кончился, не о чем, а `graceEndsAt` у сессии без события нет — считать его не от чего, и клауза по сроку ей не годится ни в каком виде.

**Почему условие заведения несёт клаузу «живой ad-hoc-сессии с этим** `appKey` **нет», и цена её отсутствия названа, потому что она уплачивалась бы каждым** `tick`**.** До v6 §8.6 такой клаузы не нёс, а §5.4 ни одним правилом не относил сигнал к уже заведённой ad-hoc-сессии — то есть сигнал оставался «не отнесённым ни к одной сессии» и после заведения, и всякий следующий `tick` заводил по нему **новую** сессию с **новым** спросом, без предела. **§9.1 свою клаузу («если у встречи нет живой сессии») печатает с издания v2; §8.6 своей не печатал ни в одном издании.** Реализация части B ([MEE-300](<https://linear.app/easypto/issue/MEE-300>)) бесконечного заведения не делает — и это её решение, а не исполнение контракта. **Цена названа прямо: правило, которого в контракте нет, реализатор пишет сам, и два реализатора напишут его по-разному**, а критерий, спрашивающий о другом, зелен у обоих.

**Ad-hoc спрашивает всегда, кроме** `.manual`**, и при** `.auto` **тоже.** **Довод:** `.auto` есть согласие записывать **запланированное**; созвон, которого нет в календаре, пользователь не планировал, и цена ошибки здесь несимметрична — запись разговора, который человек не собирался записывать, дороже пропущенной записи. §3.2 называет для ad-hoc уведомление «Записать?» и не обусловливает его политикой. **При** `.manual` **спрос не поднимается вовсе** — политика говорит «только по команде», и спрос был бы её нарушением; запись начинается командой `startRecording(meetingId: nil)`.

**Цена названа:** при `.auto` пользователь получает спрос на каждый незапланированный созвон. **Условие пересмотра:** если это окажется дорого на живом применении, лечится оно настройкой в C-016, а не молчаливым автозапуском здесь.

#### 8.7 `Processing`: цепочку конвейера строит эта машина

**C-013 называет её строителем прямо** («Поведение»: цепочку строит домен, `SessionCoordinator` подписан на `events()` и ставит следующую задачу по `succeeded` предыдущей). Здесь это записано порядком:

`transcode(recordingId)` → `transcribe(recordingId, profileId, language: nil)` → `diarize(recordingId, profileId)` → `attribute(transcriptId, meetingId)`

* первая задача цепочки ставится при входе в `processing` строкой 12;
* **восстановительный вход в** `processing` **по §10 — второй и последний вход, при котором машина ставит задачу, и он назван здесь, потому что без него встреча остаётся в** `processing` **навсегда.** При нём ставится **ровно одна** задача — первая по порядку цепочки, у которой у этой записи нет ни успешно завершённой задачи, ни задачи, ждущей исполнения или идущей. Определяется это **теми же задачами записи** (`jobs(status:)`, C-013), которыми §10 уже определяет, дошла ли цепочка до успешной `attribute`: второго чтения и второго источника не заводится. **Чем именно различаются три названных класса задач, говорит C-013; своего перечисления его статусов этот контракт не заводит** (§0, правило о чужих терминах);
* следующая ставится **по** `JobEvent.succeeded` **предыдущей и ни по какому иному событию**; два названных входа этого не отменяют — они цепочку **заводят**, а не продолжают, и третьего входа нет (инвариант 20);
* `profileId` — `AppSettings.defaultProfileId`; задачи собираются `JobSubmission.standard(_:runAfter:)` с `runAfter == now`;
* `transcriptId` для `attribute` машина берёт из хранилища (заголовок транскрипта записи, C-010), потому что `JobEvent.succeeded` несёт только `jobId` и тип; `jobId` разрешается в нагрузку методом `job(id:)` (C-013), поле `Job.payload`;
* `meetingId` у `attribute` равен `meetingId` сессии и равен `nil` у ad-hoc;
* `JobEvent.blocked` — **не отказ**: сессия остаётся в `processing`, задача ждёт своих условий (питание, тепловое состояние, идущая запись). Сказано пунктом, потому что молчание читалось бы как «блокировка есть провал»;
* `summarize` в Срезе 1 не ставится: обработчик не зарегистрирован (C-013).

**Почему возобновителем цепочки назван** `start(now:)`**, а не отдельное событие, — с ценой обоих.** **Взято:** восстановительный вход §10 ставит задачу сам. **Довод:** §10 уже читает задачи записи, чтобы решить, входить ли в `processing`, — данные для выбора следующей задачи у него на руках, и второго чтения не нужно; а единственность точки постановки, ради которой написано «и ни по какому иному событию», сохраняется, потому что входов ровно два, оба названы поимённо и оба проверяемы перебором. **Цена выбранного названа:** оговорка «ни по какому иному» перестаёт быть безусловной, и реализация, поставившая задачу из третьего места, ловится не буквой инварианта, а перечислением двух входов — то есть критерий обязан подавать оба и запрещать третий. **Отвергнуто — завести отдельное событие возобновления:** издателя, кроме того же `start(now:)`, у него не было бы, то есть это переименование взятого; а звать издателем очередь значит править C-013 — чужой контракт, `interface-request`, свой фейк и свои критерии — ради того, что закрывается одной строкой в своём.

**Повторная обработка сессию не оживляет.** `retryJob` и `retranscribe` (C-016) заводят задачи и меняют строки хранилища; терминальная сессия остаётся терминальной (§7). **Цена названа, и это дыра, которую я называю, а не прячу:** встреча, у которой обработка провалилась и была успешно перезапущена пользователем, останется в `MeetingStatus.failed` до тех пор, пока её статус не обновит **кто-то**, а этого «кого-то» сегодня нет ни в одном контракте. Это строка отчёта с владельцем и сроком, а не молчание.

### 9. `Scheduler` — раздел этого контракта, а не отдельный контракт

**Решение:** `Scheduler` описан здесь, вторым лицом одной машины, а не собственным контрактом.

**Довод — три части, и каждая проверяема.** **Первая:** словарь у них общий дословно — окно события, `armLeadSeconds`, `askLeadSeconds`, `graceEndsAt`; разделив тексты, проект получил бы **два** определения окна и сроков либо ссылку из одного в другой на каждое второе предложение. **Вторая:** передача между ними — это **один** переход (строка 2), и два контракта описывали бы каждый свою половину одного перехода, а шов оказался бы ничьим. **Третья:** П4 закрыт нулём у обоих, реализатор один (`domain-core`, DEV-2), и одна пара «критерии + план» дешевле двух.

**Цена выбранного названа:** правка таймерной политики есть издание всего контракта и дельта по всей его паре, а не по половине. **Цена отвергнутого выше:** второе определение окна — молчаливое расхождение, а не дорогая правка.

#### 9.1 Что Scheduler заводит и чего не заводит

* **сессия заводится для события, у которого** `isAllDay == false` **и** `isCancelled == false`**, при** `now ≤ graceEndsAt`**, если у встречи нет живой сессии** (инвариант 4) **и её хранимый** `MeetingStatus` **не терминален — то есть не равен ни** `ready`**, ни** `failed`**, ни** `skipped` (инвариант 24). **Две последние клаузы разведены намеренно, потому что субъекты у них разные:** первая не даёт завести вторую сессию **сейчас**, вторая не даёт завести её **потом**, в том числе после перезапуска приложения. Это **одно** условие заведения на весь контракт: строки 1, 1а и 1б §7 стоят на нём дословно и различаются только тем, **в какое состояние** сессия заводится;
* **состояние заведения есть функция от** `now`**, а не всегда** `scheduled`**:** `now < armAt` — `scheduled` (строка 1); `armAt ≤ now < e.start` — `armed` (строка 1а); `e.start ≤ now ≤ graceEndsAt` — `awaitingSignal` (строка 1б). **Сессия заводится в то состояние, в котором она была бы, будь событие известно машине вовремя,** и ни один срок при этом не «догоняется»: `armAt`, `askAt`, `e.start` и `graceEndsAt` считаются от `e.start` и от момента заведения не зависят ни на секунду — тот же довод, которым §8.3 отказывает подписке в праве сдвигать grace;
* **события на весь день сессий не порождают.** Довод: сутки — не окно созвона, и взведение на сутки держало бы машину без единого признака созвона; такой созвон ловится входом ad-hoc (§8.6);
* **отсутствие** `conference` **заведению не мешает.** Ссылка на созвон живёт и в `bodyText`, и в `location` (C-009 §2), а взведение дёшево: запись всё равно требует звучащей цели;
* `plan(now:)` возвращает `ScheduledArm` для всех таких событий по возрастанию `armAt`, при равенстве — по `meetingId`; сессий это не заводит и состояния не меняет — **чистая функция** от содержимого хранилища, настроек и `now`. **«Таких» разобрано по клаузам, а не оставлено читателю, и это издание v6:** событие входит в ответ, если истинны три первые клаузы условия заведения — `isAllDay == false`, `isCancelled == false`, `now ≤ graceEndsAt` — **и** хранимый `MeetingStatus` встречи не терминален; клауза «у встречи нет живой сессии» к `plan(now:)` **не применяется** — встреча с живой сессией в плане стоит. **Ответа это не меняет ни на одном входе: обе половины уже были вынуждены инвариантом 17, и сказано здесь то, что он уже требовал, а §9.1 не говорил.** Довод читается на его трёх ветвях: ветвь «заведённая раньше и живая» была бы **недостижима**, исключай план встречи с живой сессией; а строка плана у встречи с хранимым терминальным статусом **нарушала бы инвариант 17 целиком** после перезапуска приложения: сессии ей не даёт инвариант 24, ветвь «терминальная, если она уже ушла … **строками таблицы**» говорит о сессии этого запуска, а её нет ни одной. **Цена названа:** `nextDeadline(now:)` держит `armAt` встречи с живой сессией (инвариант 15), и composition root зовёт `tick`, который по этой встрече ничего не меняет. **Отвергнуто — сузить план до встреч без живой сессии:** это убило бы ветвь инварианта 17 молча, а цена мёртвой клаузы этим контрактом уже названа дважды — верхней границей строки 2 §7 и клаузой строки 9.

`ScheduledArm.armAt` **в прошлом законен, и читатель обязан это знать.** Строка плана с `armAt < now` означает встречу, о которой машина узнала поздно, — её сессия заводится сразу в `armed` либо в `awaitingSignal`. **До v2 такая строка плана была неисполнима:** §9.1 клал её в план, а §7 сессии ей не давал, и инвариант 17 не мог быть исполнен ни одной верной реализацией. Разобрано в §«Ломающие изменения против v1», п. 1.

**Почему выбрано расширение заведения, а не сужение §9.1, — с ценой обоих.** **Отвергнуто — сузить §9.1 до** `now < armAt`**:** это дефект не закрывает, а переносит его в §10. Перечень Б §10 восстанавливает встречи в `scheduled`, `armed` и `awaitingSignal` «заново по §9.1»; при суженном §9.1 приложение, перезапущенное после `armAt`, не завело бы сессии **ни одной** идущей встрече, и та повисла бы в своём `MeetingStatus` без машины — ровно тот исход, который §10 и написан предотвращать. Сверх того §5.4 уже сегодня относит сигналы к сессии на всём отрезке `armAt ≤ now ≤ graceEndsAt`, а §8.1 объявляет ранний вход целью взведения: из трёх мест, говорящих об окне, широки два, а узко ровно одно — строка 1. **Цена взятого названа:** таблица §7 растёт на две строки, инвариант 17 разбирается по трём случаям вместо одного, а заведение обязано смотреть, не было ли у встречи сессии, — иначе пропущенная встреча заводилась бы заново каждым `tick` на всём окне.

**Вторая сессия на одну встречу не заводится ни в одном запуске приложения, и решение об этом машина читает в хранилище, а не помнит.** Терминальный `MeetingStatus` — `ready`, `failed`, `skipped` — заведение останавливает. **Довод:** инвариант 18 обязывает записать смену состояния сессии `setStatus`-ом **прежде** публикации снимка, значит `skipped` в строке встречи и есть уже записанное решение — команды `skip`, ответа `.skip`, отмены события либо истёкшего grace. Читать записанное дешевле, чем заводить второе место для той же памяти.

**До v3 правило стояло на памяти запуска, и это была его беда, а не цена.** Заведение смотрело, есть ли у встречи сессия **этого запуска**, и в хранилище не смотрело; §10 перечень Б отказывал терминальной встрече в момент `start(now:)`, а первый же `tick` заводил ей сессию заново — сессии этого запуска у неё нет. **Отсюда прямо: человек нажал** `skip`**, приложение перезапустилось внутри окна до** `graceEndsAt`**, и его решение отменено сроком.** Разобрано в §«Ломающие изменения против v2».

**Поведение, зависящее от того, перезапускали ли приложение, дороже дорогого поведения по второй причине, и она названа:** его не воспроизвести на заданных тестом часах (§4), потому что перезапуск — не момент времени, а событие среды. Правило, читающее хранилище, от запуска не зависит и проверяется целиком на фейках репозиториев.

**Цена взятого названа и не спрятана:** встреча, отменённая в календаре и восстановленная внутри окна до `graceEndsAt`, второй сессии не получает **ни в одном запуске** — её `MeetingStatus` остался `skipped`, а восстановление события его не снимает. Ловится она входом ad-hoc (§8.6) — **и только им**; запись выйдет с `meetingId == nil`, и связать её со встречей будет нечем. **Прежняя редакция называла здесь вторым средством перезапуск (§10), и это был ложный адрес:** §10 отказывал, а заводила следующая `tick`.

**Цена эта мала ровно потому, что две причины** `skipped` **из трёх закрываются другими клаузами того же условия, и это проверяется, а не предполагается:** `skipped` по истёкшему grace недостижим для заведения — окно закрыто тем же `now ≤ graceEndsAt`; `skipped` по отмене недостижим, пока событие отменено, — его держит `isCancelled == false`. **Различение нужно ровно на одной границе:** решение человека против отменённого и **восстановленного** события.

**Отвергнуто — различать причину терминального состояния,** чтобы решение человека переживало перезапуск, а отмена календаря — нет. **Цена отвергнутого:** `MeetingStatus` (C-010 §5) причины не несёт, и хранить её негде, кроме нового значения или новой колонки у C-010, — то есть `interface-request` к чужому контракту, его издание, его дельта критериев и его дельта плана проверки ради поля, у которого один читатель.

**Условие пересмотра названо, и оно прямо открывает путь к отвергнутому:** замер, показывающий, что отмена с восстановлением внутри окна — частый вход, а не редкость, переводит это правило в `interface-request` к C-010 на причину терминального состояния; тогда клауза сужается с «всякое терминальное значение» до «всякое, кроме поставленного отменой», и §9.1 переиздаётся. **Взятое сегодня этого не запирает ничем:** оно правит место, где ответов было два, и третьего не заводит.

**Отвергнуто и второе — снимать терминальный статус по** `CalendarChange`**, принёсшему событие с** `isCancelled == false`**.** **Цена отвергнутого не в сложности, и потому она решает:** машина не различает изменение, снявшее отмену, от всякого иного изменения того же события, — а значит обычный сдвиг времени встречи, которую человек уже пропустил командой, снял бы её `skipped` и завёл сессию заново. **Это тот же дефект, что здесь чинится, только на другом входе**; правило, стоящее на несверенном признаке, даёт ответ, но молча (§5.4).

#### 9.2 Календарь изменился

* **событие сдвинулось вперёд** так, что `now < armAt` — сессия возвращается в `scheduled` (строка 5) и взводится заново по новому окну;
* **событие сдвинулось назад** — сроки пересчитываются на месте; если новый `graceEndsAt` уже прошёл, сессия уходит в `skipped` (строка 3);
* **событие отменено (**`isCancelled == true`**) или удалено** — сессия уходит в `skipped` (строки 3, 4, 9). `isCancelled` не есть удаление (C-005), и встреча остаётся в списке;
* **ни изменение окна, ни отмена, ни удаление события не трогают сессию в** `recording`**,** `stopping` **и** `processing`**.** Довод: запись уже идёт, и календарь о ней ничего не знает — отменённое в календаре событие не делает несостоявшимся созвон, который в эту минуту звучит; остановку решает §8.4.

#### 9.3 Сон и пробуждение

* на всё время `recording` и `stopping` держится `PowerActivityToken` с `reason == .recording` (C-008), взятый при входе в `recording` и отпущенный **при выходе из множества** `{recording, stopping}` — **по любому пути таблицы §7, которым машина из этого множества уходит:** строкой 12 (`stopping → processing`), строкой 13 (`stopping → failed`) и строкой 11 (`recording → failed`, минуя `stopping`). **Строка 11 названа поимённо потому, что до v2 её не покрывала ни одна буква инварианта 19,** и по букве момента отпускания не было вовсе;
* `PowerEvent.didWake` → `reschedule(now:)` и `tick(now:)`. **Сроки, пройденные во сне, исполняются первым** `tick` **после пробуждения** — это инвариант 14 дословно, отдельного правила для сна не заводится;
* `PowerEvent.willSleep` записи не останавливает: разрывы шкалы и маркеры сна — предмет C-004 и C-002.

### 10. Восстановление после перезапуска приложения

`start(now:)` **восстанавливает машину из хранилища, и правило тотально по обоим перечислениям — по** `RecordingStatus` **и по** `MeetingStatus` **(C-010 §5).** Читаются они в названном порядке: сперва записи, потом встречи.

**Порядок «заведение против проверки сроков» назван для** `start(now:)` **прямо, и это издание v6** — находка 7 дельты `Г` перечня [MEE-277](<https://linear.app/easypto/issue/MEE-277>), чей срок наступил с выдачей задачи на §10. `start(now:)` **не исполняет ни одного срока.** Он читает хранилище, приводит `RecordingStatus` к фактическому состоянию, заводит сессии перечнями А и Б — и на этом кончается. **Всякий срок, уже прошедший к моменту** `start(now:)`**, исполняется первым** `tick(now:)` **после него, строками таблицы §7 в их порядке** — то есть ровно так же, как срок, пройденный во сне (§9.3), и ровно то, что инвариант 14 говорит дословно: переход по сроку наступает не позже первого `tick` с `now ≥ срок`.

**Что заставляет этот первый** `tick` **прийти немедленно, названо здесь же и не оставлено composition root на усмотрение:** сессия, заведённая при уже прошедшем сроке, даёт `nextDeadline(now:)` в прошлом (инвариант 15), а §8.5 обязывает звать `tick` **не позже ближайшего** `nextDeadline(now:)`. Второй обязанности composition root этим не заводится ни одной — исполняется уже стоящая.

**Довод, почему взято это, а не «**`start` **исполняет сроки сам», — с ценой обоих.** **Взято:** заведение предшествует сроку и в `start(now:)`, и в `tick` («Поведение»: сперва события, затем оценка и цель, затем сроки в порядке строк §7), то есть у одного вопроса один ответ, а не два. §9.1 говорит дословно, что **ни один срок при заведении не «догоняется»**; `start`, исполняющий сроки в том же проходе, был бы исключением из этой фразы, а исключения у неё нет. **Цена выбранного названа:** потребитель, прочитавший `changes()` **между** `start(now:)` и первым `tick`, увидит сессию в `awaitingSignal`, чей `graceEndsAt` уже прошёл; снимок верен на свой момент и сменится первым же `tick`, но «верен» здесь значит «не противоречит таблице», а не «приятен читателю». **Цена отвергнутого выше:** §10 обязан был бы повторить у себя проход по таблице §7 целиком — то есть завести **второе** место, где написан порядок строк, ровно того класса, который издания v3 и v5 из этого контракта убирали; и первый же `tick` после такого `start` читал бы таблицу второй раз на том же `now`.

**Половина этой находки про** `tick` **закрыта не изданием, а чтением, и это записано, чтобы её не закрывали второй раз:** абзац «Поведение» называет порядок фаз, и «в порядке строк §7» решает случай `now == graceEndsAt` — заводящая строка стоит раньше строки 9 и побеждает.

| `.recording`, `.stopping` | `recover(directory:)` (C-004). **Удалось** — машина **сперва приводит** `RecordingStatus` **этой записи к** `.finalized` (`RecordingRepository.save(_:)`, C-010, с восстановленным манифестом), **и только затем** сессия входит в `processing` **и ставится первая недошедшая задача цепочки (§8.7)**. **Бросил** `recoveryFailed` — машина приводит `RecordingStatus` к `.failed`, и сессия входит в `failed`. `origin` берётся из `manifest.meetingId`: `nil` — `.adHoc` |
| `.finalized` | сессия входит в `processing` тогда и только тогда, когда цепочка §8.7 этой записи не дошла до успешной `attribute` **и ни одна её задача не завершилась отказом или отменой**; определяется это задачами записи (`jobs(status:)`, C-013), а не статусом встречи. Войдя, машина **ставит первую недошедшую задачу цепочки** (§8.7). **Есть задача, завершившаяся отказом или отменой, — сессия входит в** `failed`**:** это тот же исход, который строка 15 даёт живой машине, и повторную обработку заводит команда пользователя (§8.7), а не восстановление |
| `.failed` | сессии не заводит |

**Восстановительный вход в** `processing` **ставит задачу сам, и это издание v2.** В v1 §10 умел определить, что цепочка не дошла до `attribute`, и не умел её продолжить: постановка задачи была привязана инвариантом 20 к `JobEvent.succeeded` предыдущей «и ни по какому иному событию», а `succeeded`, на который можно было опереться, произошёл до перезапуска и в живом потоке `events()` больше не придёт. **Цена умолчания названа перечнем и подтверждена приёмкой:** встреча, у которой приложение перезапустили посреди обработки, оставалась в `processing` **навсегда** — ни `ready`, ни `failed`, — а поправить её статус, по §8.7, сегодня некому.

`RecordingStatus` **приводится к фактическому состоянию машиной, и это издание v4.** До него §10 звал `recover`, вводил сессию в `processing` либо `failed` — и оставлял строку `recordings` в `.recording`: **та же запись возвращалась из** `unfinalized()` **(C-010) при каждом следующем запуске, и** `recover` **звался на ней снова.** Дубликата задачи это не давало (§8.7 не ставит задачу, у которой уже есть ждущая или идущая), но запись не финализировалась никогда. **Обязанность названа не здесь, а у соседа, и здесь она только исполняется:** C-010 («Поведение») говорит, что строка `recordings` со статусом `recording` при старте означает прерванную запись, что обработка — «дочитать манифест с диска, финализировать или пометить `failed`» — **обязанность домена, а не репозитория**, и что `unfinalized()` существует именно для этого. **Порядок значим по тому же доводу, что в инварианте 18:** сперва запись, потом вход в `processing`, иначе падение между ними оставляет запись нефинализированной, а цепочку — поставленной.

**Б. По встречам (**`MeetingStatus`**):**

| Значение | Что делает `start` |
| -- | -- |
| `scheduled`, `armed`, `awaitingSignal` | сессия заводится заново по §9.1, и все сроки считаются от `now`; поднятый до перезапуска спрос не восстанавливается и при `.ask` поднимается заново |
| `recording`, `stopping`, `processing` | сессию определяет запись этой встречи по перечню А. **Если записи у неё нет ни одной, статус встречи ложен** — машина ставит `failed` и называет это в логе: иного способа отличить «запись потеряна» от «статус не дописан» у неё нет. **Сессии при этом не заводится ни одной, и это сказано здесь, а не выведено читателем** (издание v7): заведений сессии вне таблицы §7 ровно **два**, оба в перечне А (инвариант 2), и перечень Б третьего не заводит; `setStatus` зовётся тут без сессии, потому что менять состояние нечему |
| `ready`, `failed`, `skipped` | сессия не заводится, и это **следствие**, а не второе правило: §9.1 не заводит сессии для встречи с терминальным `MeetingStatus` (инвариант 24), и `start(now:)` здесь не исключение. Строка оставлена ради тотальности перечня по `MeetingStatus` (инвариант 22). Пара «терминальная встреча при незавершённой записи» разрешается в пользу перечня **А**, как сказано ниже: судьбу **записи** решает А, и заведение по §9.1 её не касается |

**Два перечня не спорят по построению:** перечень А решает судьбу **записи**, перечень Б — судьбу **встречи**, и встреча в `recording`, `stopping` или `processing` берёт свой исход из А, а не решает его сама. Пара «встреча в `ready` при записи в `.recording`» разрешается в пользу А: сессия входит в `processing` и доводит цепочку, а `setStatus` приводит встречу к фактическому состоянию (инвариант 18).

**Довод за** `recover`**:** оборванная запись — штатный вход C-004, у него есть названный метод, и второго способа собрать манифест из каталога в проекте нет. **Цена названа:** ответ на «что делать с записью, прерванной падением» лежит в `capture`, а машина берёт его исход; если `recover` бросит `recoveryFailed`, сессия уходит в `failed`, и файлы остаются на диске — удаляет их пользователь командой фасада, а не машина.

### Инварианты

Утверждения ниже — требования этого контракта. Счёта их здесь нет намеренно: он устаревал бы от каждого нового пункта; число на сегодня стоит в отчёте об издании, где его можно пересчитать по тексту.

**По умолчанию инвариант проверяется тестами реализатора машины (**`domain-core`**), то есть работой CI** `Core (Linux)`**, на фейках портов из** `DomainTestKit` **и на заданных тестом моментах (**`now` **— параметр, §4).** Умолчание верно почти везде, и **исключения названы поимённо, потому что молчаливое исключение означает «не проверяет никто»**:

* **вторая половина инварианта 9 и обязанность composition root звать** `tick` **достаточно часто и пользоваться ответом** `nextDeadline(now:)` — **не проверяется ни одной работой CI**: субъект у неё `app-ui`, которого сегодня нет ни строкой, а проверяемая половина («машина, получив `tick`, исполняет срок») остаётся у машины. **Инвариант 15 в это исключение не входит и проверяется целиком:** он говорит о **значении, которое возвращает** `nextDeadline(now:)`, а не о том, кто и как часто этим значением пользуется, и на фейках портов проверяется обеими половинами «тогда и только тогда». **До v2 исключение называло «весь инвариант 15», то есть было шире, чем есть,** и снимало проверку с функции, объявленной §3.2 ради проверяемости;
* **инвариант 19** (`PowerActivityToken` держится всю запись) проверяется на `DomainTestKit.FakePowerPort` счётом взятых и отпущенных токенов; **что система при этом действительно не уснула, не проверяется ничем автоматическим** — вход для этого создаётся только руками;
* **инвариант 13** (одна группа — одна запись) проверяется полностью здесь, а **его следствие в захвате** — что два tap-а на одну группу не создаются, — предмет C-004 и этой проверкой не закрывается.

**Кого эти утверждения связывают, когда значение подаёт фейк.** `DomainTestKit.FakeProcessMonitorPort` инвариантами публикующей стороны C-009 не связан (C-009, шапка раздела «Инварианты»), и это здесь **используется намеренно**: вход «негодный сигнал от сломанного адаптера» — например `clientAudioOutput` с `group == nil` — тест подаёт через фейк, и правила §5.3 обязаны его пережить. Из того, что фейк вправе отдать, не следует ни одного разрешения реализатору `detector`.

 1. **Состояние сессии есть одно из девяти значений** `MeetingStatus` **(C-010 §5).** Второго перечисления состояний этот контракт не заводит, и отображения между двумя перечислениями не существует, потому что перечисление одно.
 2. **Переходы — только строки таблицы §7, в её порядке; первое подошедшее условие побеждает.** Всякий иной переход запрещён. Отображение «состояние × вход → состояние» тотально: вход, не названный ни одной строкой для текущего состояния, состояния не меняет и ошибки не даёт. **Исключение ровно одно, оно названо поимённо и счётно: восстановительное заведение сессии в** `start(now:)` **по §10, перечню А — вход в** `processing` **и вход в** `failed`**, два способа и ни одного третьего.** **Заведение ad-hoc-сессии исключением не является и им никогда не объявлялось: оно описано строками 1в и 16 таблицы, и это издание v6.** До него §8.6 заводил ad-hoc-сессию прозой, ни одной строкой не описанной, — то есть **третьим** способом вне таблицы при счёте «два»; отсюда настоящий пункт был **ложен на собственном тексте контракта**, а его проверяемая форма ниже — неисполнима ни одной верной реализацией, потому что требовала отсутствия того, что контракт тут же требовал завести. Живых переходов это исключение не касается: всё, что происходит с уже заведённой сессией, — строки таблицы и только они. **Проверяемая форма:** перебор подаёт `start(now:)` на всяком содержимом хранилища и требует, чтобы сессии вне таблицы заводились ровно этими двумя способами, а всякий третий отсутствовал.
 3. `ready`**,** `failed` **и** `skipped` **терминальны:** исходящих переходов у них нет ни одного, и ни один вход их не меняет. Команда, адресованная терминальной сессии, бросает `SessionError.sessionIsTerminal(sessionId:state:)`.
 4. `meetingId == nil` **тогда и только тогда, когда** `origin == .adHoc`**.** На одну встречу в один момент существует не более одной нетерминальной сессии, **а после того, как сессия встречи стала терминальной, второй не заводится ни в одном запуске приложения** (инвариант 24). **На одну цель в один момент существует не более одной нетерминальной ad-hoc-сессии:** не бывает двух нетерминальных сессий с `origin == .adHoc` и равным `appKey` **цели, назначенным при заведении** (§5.4, правило 1а). **Опознаётся ad-hoc-сессия назначенным при заведении** `appKey`**, а не** `SessionSnapshot.target`**, и это правка издания v7:** прежняя редакция сравнивала `target?.appKey`, а `target` есть цель **актуальная** (§5.3) и обращается в `nil` на всякий срок §8.4, пока запись жива, — то есть две ad-hoc-записи с погасшими целями несли `target?.appKey`, равный `nil` у обеих, и пункт объявлял запрещённым состояние, которого не запрещает ничто. **Назначенный** `appKey` **от актуальности не зависит ни на секунду**, и ровно на нём стоят и правило 1а §5.4, и клауза условия заведения §8.6 («живой ad-hoc-сессии с этим `appKey` нет»), — то есть этой правкой пункт приводится к двум местам, которые уже говорили так. **Половины этого пункта разведены намеренно, потому что субъекты у них разные и правила тоже:** у сессии события тождество даёт `meetingId` и помнит его хранилище (инвариант 24); у ad-hoc-сессии тождества в хранилище нет вовсе — `meetingId` у неё `nil`, — и единственный её признак есть `appKey` цели, живущий в памяти приложения. **Отсюда прямо и без умолчания: после перезапуска приложения ad-hoc-сессия, не дошедшая до записи, не восстанавливается ничем** — §10 перечень А поднимает только те, у которых есть строка `recordings`, — и спрос по той же цели будет поднят заново, если цель ещё актуальна. **Это не дефект и не цена этого пункта, а прямое следствие §1.1** («сессия живёт в памяти приложения»), и названо оно здесь потому, что молчание читалось бы как обещание обратного.
 5. `recordingId` **равен** `nil` **во всех состояниях до** `recording`**; при входе в** `recording` **он назначается и дальше не меняется ни в одном состоянии, включая терминальные.**
 6. **Оценка считается формулой C-009 §1 над сигналами, отнесёнными к сессии (§5.4) и актуальными по инварианту 25 C-009, включая собственный календарный сигнал §5.2, и ничем иным.** Своего определения актуальности, своего срока и своей формулы у машины нет: прогон по тексту даёт **ноль** таких определений.
 7. **Оценка не служит условием ни одного перехода.** Различающий вектор назван прямо: набор «окно события и пять запущенных клиентов, ни одного `clientAudioOutput`» даёт `estimate > 0,9` и **не** переводит сессию в `recording` ни при какой политике.
 8. **Календарный сигнал сессии удовлетворяет инвариантам 11, 12 и 17 C-009:** `weight == weights.calendarWindow` таблицы весов, `pid == nil`, `meetingId == e.id`, `group == nil`. Сигнал существует тогда и только тогда, когда `e.start ≤ now < e.end`.
 9. **Разрыв по** `observedAt` **между двумя построениями календарного сигнала одной сессии меньше** `signalTtlSeconds` — исполнение инварианта 24 C-009 публикующей стороной. Проверяемая половина: два `tick` с разрывом меньше срока дают два сигнала с разрывом меньше срока. Вторая половина — что `tick` приходит достаточно часто — лежит на composition root и CI не проверяется.
10. **Правила разогрева у машины нет:** пустой набор сигналов при подписке значит «сигналов нет», и `graceEndsAt` от момента подписки не зависит ни на секунду. Различающий вектор: сессия, заведённая посреди идущего созвона, находит цель в снимке подписки и переходит в `recording` **до** истечения `signalTtlSeconds` от подписки.
11. **Подписка на** `ProcessMonitorPort.signals()` **— одна на приложение.** Две сессии, живущие одновременно, считают оценку по одному и тому же набору публикаций; набор сигналов, отнесённых к каждой, — функция от §5.4, а не от того, кто когда подписался.
12. **Звучащая цель определена §5.3, и её выбор детерминирован и тотален:** на одном и том же наборе сигналов и одном `now` две реализации выбирают одну и ту же группу. Сигнал `clientAudioOutput` с `group == nil` целью не является (вход от негодного адаптера), и машина на нём не падает.
13. **Одна группа — одна запись:** не существует двух сессий в состояниях `recording` или `stopping`, у которых `target` **не** `nil` **и** `target!.appKey` **равны**. **Оговорка про** `nil` **заведена изданием v7 и не формальна — вход достижим:** звучащая цель есть цель **актуальная** (§5.3), а запись переживает утрату цели на весь срок §8.4, — то есть две записи, у которых цели перестали быть актуальными в один и тот же `tick`, обе несут `target == nil`, и прежняя редакция объявляла такое состояние запрещённым. **§7.1 его не запрещает и запрещать не должен:** занятость там проверяется по **названному** `appKey` цели, а `nil` не равен ни одному, — то есть два места давали два ответа на один вход, и верен ответ §7.1.
14. **Переход по сроку не наступает раньше своего срока и наступает не позже первого** `tick(now:)` **с** `now ≥ срок`**.** Это относится ко всем срокам контракта: `armAt`, `askAt`, `e.start`, `graceEndsAt`, срок §8.4.
15. `nextDeadline(now:)` **не больше ближайшего срока любой живой сессии и ближайшего** `armAt` **из** `plan(now:)`**;** `nil` он возвращает тогда и только тогда, когда сроков нет ни одного.
16. `plan(now:)` **— чистая функция** от содержимого хранилища, `AppSettings` и `now`: повторный вызов с тем же входом даёт тот же ответ, порядок ответа не зависит от порядка строк хранилища, и вызов не меняет состояния ни одной сессии.
17. **Ответ** `plan(now:)` **согласован с поведением, и согласие тотально по строкам плана.** Для всякой строки `plan(now:)` сессия её встречи существует не позже первого `tick(now:)` — заведённая строкой 1, 1а или 1б по правилу §9.1, либо заведённая раньше и живая, либо терминальная, если она уже ушла в `skipped`, `failed` или `ready` строками таблицы. **Состояние сессии, заведённой по строке плана, есть функция от** `now` **заведения:** при `now < armAt` она заводится в `scheduled` и оказывается в `armed` **не раньше** `armAt` **и не позже первого** `tick` **с** `now ≥ armAt`; при `armAt ≤ now < startsAt` — сразу в `armed`; при `startsAt ≤ now ≤ graceEndsAt` — сразу в `awaitingSignal`. При `recordingPolicy == .ask` спрос поднимается по тому же правилу относительно `askAt`, а у сессии, заведённой при уже прошедшем `askAt`, — в момент заведения; при других политиках `askAt == nil` и спрос не поднимается.
18. **Всякая смена состояния сессии с** `meetingId != nil` **записывается** `MeetingRepository.setStatus(_:meetingId:)` **(C-010) прежде, чем машина опубликует снимок в** `changes()`**.** Порядок значим: иначе потребитель, прочитавший хранилище по событию, прочтёт прежнее значение. **Команда §3.1, уводящая сессию в терминальное состояние (**`skip`**, ответ** `.skip` **через** `answer`**), возвращает управление не раньше, чем её исход записан этим вызовом.** Отсюда граница окна названа точно, а не умолчана: падение до возврата команды теряет решение — и человек не получил подтверждения; падение после возврата решения не теряет. **Что даёт возврат** `setStatus` **для долговечности записи — предмет C-010** («Поведение»: один вызов репозитория — одна транзакция), и своего определения этот контракт не заводит.
19. **На всё время состояний** `recording` **и** `stopping` **держится ровно один** `PowerActivityToken` **с** `reason == .recording` **(C-008);** он берётся при входе в `recording` и отпускается **при выходе из множества** `{recording, stopping}` — **по любому пути, которым машина из этого множества уходит**, в том числе строкой 11 (`recording → failed`, минуя `stopping`) и строкой 13 (`stopping → failed`). После выхода из множества не держится ни один токен: взятых и отпущенных поровну, остаток нулевой.
20. **Цепочка обработки:** `transcode` **→** `transcribe` **→** `diarize` **→** `attribute`**.** Следующая задача ставится по `JobEvent.succeeded` предыдущей и ни по какому иному событию. **Входов, при которых машина ставит задачу не по** `succeeded`**, ровно два, и оба названы поимённо:** вход в `processing` строкой 12 — первая задача цепочки; **восстановительный вход в** `processing` **по §10 — первая недошедшая задача цепочки** (§8.7). ## Поведение

* **Машина решает, фасад собирает.** `SessionCoordinator` не строит моделей чтения UI, не публикует `AppEvent` и не знает о `AppErrorView`: он отдаёт `SessionSnapshot` и `SessionChange`, а переводит их в поверхность UI фасад (C-016, «Поведение»: фасад — тонкий слой сборки, решения принимают `SessionCoordinator`, `JobQueue` и `attribution`).
* **Команды фасада приходят сюда, а не исполняются там.** `startRecording`, `stopRecording` и `skipMeeting` (C-016 §4) — это вызовы §3.1; ошибки машины (`SessionError`) фасад переводит в `AppFacadeError` своим правилом, и словарь кодов — его предмет.
* **Порядок обработки входов в один** `tick` **назван, потому что от него зависит ответ:** сперва применяются пришедшие события (сигналы, захват, очередь, календарь, питание), затем пересчитывается оценка и звучащая цель, затем проверяются сроки в порядке строк §7. Вход, пришедший между двумя `tick`, до `tick` состояния не меняет — кроме команд §3.1, которые исполняются в момент вызова.
* **Команда сильнее политики и сильнее срока.** `startRecording` начинает запись при `recordingPolicy == .manual` и при висящем спросе; `stopRecording` останавливает запись, которую §8.4 останавливать не собирался. Довод: политика описывает **автоматику**, а команда есть прямое указание человека, и машина, отказавшая человеку ради собственного срока, не чинится ничем.
* `stop()` **подписки снимает, а идущую запись не останавливает.** Довод: `stop()` зовётся при завершении работы приложения, и остановка записи — отдельное решение, у которого есть команда; оборванная запись подбирается правилом §10 через `recover`.
* **Отказ входа не есть отказ машины.** `ProcessMonitorError.permissionRequired` (C-009) и `CalendarError` (C-005) сессий не роняют: сигналов просто нет, и сессия уходит в `skipped` по §8.3 своим сроком. Отличать «прав нет» от «созвона нет» — работа мастера прав (C-016, `permissionsReady`), а не этой машины. **Цена названа:** при не выданном праве на системный звук все запланированные сессии уйдут в `skipped`, и человек узнает причину из мастера прав, а не из состояния встречи.
* **Машина не удаляет ничего.** Ни файлов записи, ни строк хранилища, ни задач очереди: удаление — команда пользователя (C-016), политика удержания аудио исполняется отдельной операцией домена.
* **Реализация изолирована актором;** `SessionCoordinator` **и** `Scheduler` **—** `Sendable`**.** Вызываются из любого контекста; UI зовёт их через фасад.
