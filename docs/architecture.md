# Архитектура macOS-приложения для автоматической записи и транскрибации встреч

Версия 0.8 — 11 сентября 2026. Против 0.7: правка по итогам спайка захвата MEE-8 (задача MEE-65). Спайк опроверг измерением три утверждения §5.2 — «тапаем процесс браузера», «микрофон = я» и «пересборка с сохранением временной шкалы»; все три переписаны по фактам. Закрыто допущение A2: deployment target 14.2 → 14.4. Разрешены два приватных вызова для Среза 1 с названной ценой (§9.4). Добавлен §5.5 — что платформа не гарантирует. Подавление эха по корреляции каналов стало обязательным шагом конвейера, voice processing выключен по умолчанию навсегда. Пять решений внесены в журнал §12.

В версии 0.6 были зафиксированы решения по дистрибуции, платформе, оборудованию, транскрибации, размещению вычислений и назначению (личное использование) (§12); добавлен Model Manager (§6.5); движок вынесен в XPC-сервис; для русского ASR выбрана GigaAM v3 с целевым исполнителем ANE; резюме встреч заложены как расширение (§6.6).

Документ описывает компоненты, их границы и интерфейсы, выбор технологий с обоснованием и альтернативами. Кода нет намеренно; там, где интерфейс проще показать структурой (JSON-контракт, список методов протокола), приведён минимальный набросок.

## 2. Выбор платформы разработки

### 2.1 Что переносится по природе, а что нет

Прежде чем сравнивать фреймворки, полезно разложить приложение на части и посмотреть, насколько каждая переносима *сама по себе*:

| Часть | Доля усилий (оценка) | Переносимость по природе |
|---|---|---|
| Захват звука, права, фоновый режим, автозапуск, обнаружение процессов | ~25 % | Нулевая. На каждой ОС свои API (Core Audio / WASAPI / PipeWire; TCC / ничего / PolicyKit). Пишется заново при любом фреймворке |
| Коннекторы календаря | ~10 % | Сетевые (Graph, Google API) — полная; системные (EventKit, Outlook COM на Windows) — нулевая |
| Движок транскрибации и диаризации | ~25 % | Полная, если движок — C/C++/ONNX или отдельный процесс |
| Доменная логика: машина состояний встречи, хранилище, привязка спикеров, хост плагинов | ~20 % | Полная, если написана на переносимом языке; иначе переписывается |
| UI | ~20 % | Полная для web/Flutter; нулевая для SwiftUI |

Вывод: выбор фреймворка решает судьбу примерно 40 % кода (UI + домен). Остальное либо переносимо по построению (движок, сетевые плагины), либо не переносимо ни при каком выборе (системная интеграция). Electron и Tauri **не избавляют от Swift-кода захвата** — они лишь решают, где живут UI и логика. Это главное, что искажает интуицию «кроссплатформенный фреймворк = дешёвый порт».

### 2.2 Сравнительная таблица

| Критерий | Swift / SwiftUI | Electron | Tauri 2 (Rust + web) | Flutter | .NET (MAUI / Avalonia) | Qt (C++ / PySide6) |
|---|---|---|---|---|---|---|

| Новые языки для команды с Python-бэкграундом | Swift | Swift (модуль) + JS/TS | Swift (модуль) + Rust + JS/TS | Swift + Dart | Swift-биндинги + C# | C++ или Python (PySide) |

Замечание по Qt/PySide6: соблазнительно для Python-команды, но приложение с Python-рантаймом, torch и Qt весит 1 ГБ+, а системная интеграция всё равно требует ObjC-обвязки. Не рекомендую.

### 2.3 Три гибридные схемы

**Схема A — чисто нативное приложение.** Принята (§2.4).

- Swift/SwiftUI: UI, системная интеграция, доменная логика.
- Движок транскрибации — Swift-SDK (FluidAudio) в XPC-сервисе внутри бандла, за протоколами (§6.5). Переносимость движка — не цель.
- Протокол плагинов-коннекторов языконезависим: сетевые коннекторы переносятся как есть.
- Граница: всё, что трогает Apple-фреймворки, — в Swift; всё, что «математика над аудио», — в движке; всё, что «ходит в интернет за календарём», — в плагинах.
- Порт на Windows: переписать UI, захват (WASAPI process loopback), домен (если остался в Swift). Переиспользуется ~35–45 %.

**Схема B — Tauri: Rust-ядро + web UI + Swift-библиотека захвата.** Рекомендую, если Windows подтверждён на горизонте 12–18 месяцев.

- Rust: домен, хост плагинов, хранилище (rusqlite), оркестрация движка.
- Swift static library или XPC-helper: захват, права, EventKit. Связь через swift-bridge / UniFFI / C ABI.
- Web UI (React/Svelte) в WKWebView.
- Переиспользуется ~70–75 %. Цена: два дополнительных языка сразу, незрелые биндинги, реальный риск потратить недели на glue-код вместо продукта; ощущение «не совсем нативно» в menu-bar-приложении.

**Схема C — Rust-ядро + нативные UI на каждой ОС** (подход 1Password).

- Rust core через UniFFI → SwiftUI на macOS, WinUI на Windows.
- Максимально нативный UX при общей логике; максимальная стоимость и сложность сборочной инфраструктуры. Оправдано для команды 5+ человек и продукта на несколько лет.

### 2.4 Принятое решение

**Схема A: чисто macOS-приложение на Swift/SwiftUI, включая движок транскрибации.** Это решение о платформе, а не об упрощении архитектуры: глубина интеграции с macOS, изоляция процессов и качество конвейера не урезаются. Windows — «позже, но точно», но без даты, и под него не проектируем.

Что это означает на практике:

1. Один язык — Swift. Rust, web-фронтенд и Tauri не появляются; движок транскрибации — Swift-SDK (FluidAudio) в XPC-сервисе, то есть в macOS-нативной форме изоляции, а не в переносимом stdio-бинарнике.
2. Переносимость движка (sherpa-onnx как второй движок «ради Windows») снимается с v1. Второй движок может появиться только по причинам качества (например, Whisper для смешанной речи), не ради портируемости.
3. При порте на Windows заново пишутся UI, захват, домен и движок. Переезжают: сетевые коннекторы (тот же stdio-протокол), JSON-контракты данных, схема SQLite, каталог моделей. Это ~15–20 % — честная цена выбора, и при «Windows когда-нибудь» она правильная: экономия на glue-коде и втором языке сейчас больше, чем стоимость переписывания потом.

Дешёвые заделы, которые сохраняем — они почти ничего не стоят и не усложняют v1:

- доменная логика в отдельном Swift-пакете без импорта AppKit/SwiftUI (только Foundation) — упрощает тесты уже сейчас;
- системные зависимости — за протоколами: `AudioCapturePort`, `CalendarPort`, `PermissionsPort`, `ProcessMonitorPort`, `PowerPort`, `TranscriptionEngine`, `DiarizationEngine` — это нужно для подмены в тестах и для второго движка, порт тут вторичен;
- DTO — `Codable`-структуры с опубликованной JSON-схемой: плагины и облачные движки говорят на том же языке.

Точка возврата: если до старта разработки Windows получит дату в пределах 12–18 месяцев — вернуться к схеме B (§2.3). После написания SwiftUI-интерфейса и движка переход означает переписывание ~40 % кода.

## 3. Схема компонентов и потоки данных

### 3.1 Процессы

| Процесс | Что внутри | Почему отдельно |
|---|---|---|
| **App** — menu-bar-приложение (`LSUIElement`) с окнами | Calendar Hub, Platform Resolver, Scheduler, Meeting Detector, Session Coordinator, Capture Engine, Job Queue, Speaker Attribution, Storage, Permissions, UI | Ядро. Должно быть одно: владеет TCC-правами и состоянием |
| **Engine** — XPC-сервис `TranscriptionEngine.xpc` в бандле (Swift, FluidAudio) | VAD, ASR, диаризация, эмбеддинги голоса | Модели на 1–2 ГБ и их падения изолированы от записи и UI; launchd поднимает сервис по требованию и убивает после простоя — критично на M2 с 8 ГБ (§6.5) |
| **Plugin processes** — опционально, для сторонних коннекторов | Один коннектор = один процесс | Изоляция, любой язык (§4) |

Возможная эволюция — вынос Capture Engine в отдельный XPC-сервис, чтобы крэш UI не прерывал запись. В v1 не делаем: у захвата, в отличие от движка, нет проблемы с памятью, а menu-bar-приложение живёт постоянно. Capture Engine изолируется как Swift-actor с минимальной зависимостью от UI; XPC-граница зарезервирована протоколом `AudioCapturePort`.

### 3.2 Компоненты

**Calendar Hub.** Хост плагинов-коннекторов. Опрашивает коннекторы по расписанию (интервал на коннектор, плюс по пробуждению системы и по кнопке), нормализует события в `MeetingEvent`, дедуплицирует (одна встреча может прийти из Outlook и из Календаря macOS — ключ дедупа: join-URL, затем ICS UID, затем «организатор + время»), публикует изменения Scheduler'у. Интерфейс: `CalendarPort` (Swift) ↔ протокол плагина (§4).

**Platform Resolver.** Из полей события (location, body, conferenceData) извлекает `JoinInfo {provider, url, meetingId, passcode}`. Таблица правил: `zoom.us/j/`, `meet.google.com/`, `teams.microsoft.com/l/meetup-join/`, `webex.com`, `telemost.yandex.ru`, `talk.kontur.ru`, `salutejazz`, Jitsi и т. д. Вторая таблица: провайдер → bundle ID нативного клиента (`us.zoom.xos`, `com.microsoft.teams2`, `Cisco-Systems.Spark`) или «браузер». Правила — данные, не код, чтобы обновлять без релиза.

**Scheduler.** Держит таймеры на ближайшие события (взводит «боевую готовность» за T−2 мин), реагирует на изменения календаря, разруливает пересечения (две встречи одновременно — выбирается та, у которой есть сигнал от Detector; иначе спрашиваем пользователя).

**Meeting Detector.** Сливает сигналы в оценку «встреча идёт» с уверенностью:

- временное окно события (слабый сигнал);
- запущен процесс клиента созвона (`NSWorkspace.runningApplications`) — средний;
- процесс *издаёт звук* — через Core Audio: список процессов-аудиоклиентов (`kAudioHardwarePropertyProcessObjectList`) и свойства `kAudioProcessPropertyIsRunningOutput/Input` — сильный, и он же точно говорит, какой процесс тапать;
- микрофон занят каким-то процессом — средний;
- опционально позже: заголовок окна через Accessibility (для Meet во вкладке Chrome), расширение браузера.

**Session Coordinator.** Машина состояний одной встречи:

`Scheduled → Armed → AwaitingSignal → Recording → Stopping → Processing → Ready | Failed | Skipped`

Политики: автозапуск против «спросить» (уведомление с кнопкой за 30 с до старта), grace-период на опоздание (сигнала нет 15 мин после начала → `Skipped`), критерии остановки (событие закончилось *и* N минут нет звука от процесса; процесс перестал издавать звук на M минут; ручная остановка), поведение при встрече, ушедшей за расписание (продолжаем, пока есть звук). Ad-hoc созвон без события — отдельный вход в ту же машину: Detector видит звук клиента → уведомление «Записать?».

**Capture Engine** — §5. **Job Queue** — персистентная очередь в SQLite (типы: transcode, transcribe, diarize, attribute, summarize), ретраи, приоритеты, условия запуска (питание от сети, тепловое состояние, не во время записи — настраиваемо). **Engine** — реализации протоколов `TranscriptionEngine` / `DiarizationEngine` / `EmbeddingEngine` (FluidAudio, облачные), прогресс и отмена. **Model Manager** — §6.5. **Speaker Attribution** — §7. **Storage** — §8. **Permissions & System** — §9.

**UI.** Пункт в меню-баре (статус, текущая встреча, старт/стоп, ближайшие события); главное окно (список встреч, просмотр транскрипта с цветами спикеров и синхронизированным плеером, переименование спикеров, поиск); настройки (коннекторы, движки, политики записи, хранение); мастер онбординга по правам.

### 3.3 Потоки данных

1. **Синхронизация.** Plugin → `MeetingEvent[]` → Calendar Hub (нормализация, дедуп) → Storage (`meetings`, `attendees`) → Scheduler.
2. **Начало встречи.** Scheduler взводит сессию → Detector даёт сигнал с PID процесса → Coordinator переводит в `Recording` → Capture Engine открывает tap на процесс и микрофон.
3. **Запись.** Capture Engine пишет чанки на диск, шлёт уровни/статус в UI; Coordinator следит за условиями остановки.
4. **Постобработка.** Финализация файла → Job Queue → Engine (VAD → ASR по каналам → диаризация системного канала → эмбеддинги) → `Transcript` JSON → Speaker Attribution (участники + профили) → Storage (`segments`, FTS).
5. **Обратная связь.** Пользователь переименовывает спикера в UI → обновляются `segments.person_id` и голосовой профиль этого человека → следующие встречи атрибутируются лучше.

### 3.4 Контракты данных

Три структуры, которыми обмениваются процессы; у каждой — версионированная JSON-схема.

`MeetingEvent` (выход плагина):

```
id, sourceConnectorId, externalId, icalUid?
title, start, end, timeZone, isAllDay, isCancelled
organizer {name, email}
attendees[] {name, email, responseStatus, isOptional}
location?, bodyText?, conference? {provider, joinUrl, meetingId, passcode}
lastModified
```

`RecordingManifest` (выход Capture Engine): пути к файлам, раскладка каналов (`mic`, `system`), sample rate, метки времени старта/стопа/пауз, разрывы шкалы с их длительностью, PID и bundle ID **всех процессов, попавших в tap** (группа, а не один процесс — §5.2), устройства ввода.

`Transcript` (выход движка): `segments[] {startMs, endMs, channel, speakerCluster, text, words[] {startMs, endMs, text, conf}}`, `speakers[] {cluster, embedding, totalMs}`, `language`, `engine`, `modelVersion`.

## 4. Плагинная архитектура коннекторов календаря

### 4.1 Контракт плагина

Контракт описывается один раз, языконезависимо (JSON-RPC 2.0 + JSON-схемы), и имеет зеркальный Swift-протокол `CalendarConnector` для in-process реализаций. По духу это то же, что LSP или MCP: `initialize` с обменом capabilities, набор методов, уведомления, `shutdown`. Если удобно — плагинную обвязку можно буквально собрать на MCP SDK (транспорт stdio, lifecycle, схемы), хотя для v1 это скорее перебор.

Методы плагина (вызывает хост):

| Метод | Назначение |
|---|---|
| `initialize(hostInfo)` → `pluginInfo, capabilities` | Версии протокола, что умеет: delta-sync, push, участники, conference-данные |
| `getSettingsSchema()` → JSON Schema | Хост сам рендерит форму настроек; плагин не рисует UI |
| `configure(settings)` | Применить настройки |
| `beginAuth()` → `{authUrl, redirectScheme}` / `completeAuth(callbackUrl)` | OAuth-поток ведёт **хост** через `ASWebAuthenticationSession`; плагин получает только результат |
| `listCalendars()` → `Calendar[]` | Для выбора, что синхронизировать |
| `fetchEvents(range, calendarIds)` → `MeetingEvent[]` | Базовый режим: полный снимок окна (например, −1 день … +14 дней) |
| `fetchChanges(cursor)` → `{events, deleted, cursor}` | Опционально: delta-синхронизация (Graph delta, EventKit change token) |
| `healthCheck()` → status | Для индикации в UI |
| `shutdown()` | |

Сервисы хоста, доступные плагину (вызывает плагин):

| Сервис | Зачем |
|---|---|
| `secrets.get/set(key)` | Токены хранятся в Keychain **хоста** под изолированным пространством имён плагина; плагин не держит секреты на диске |
| `log(level, msg)` | Единый лог |
| `notify(kind, payload)` | «Изменения есть» для push-capable коннекторов (EventKit `EKEventStoreChanged`) |

### 4.2 Способ загрузки: сравнение

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| In-process `.bundle` с principal class | `Bundle(url:).load()`, класс реализует `CalendarConnector` | Просто, быстро, доступ к Apple-фреймворкам (EventKit) под TCC самого приложения | Нет изоляции: крэш плагина = крэш приложения; hardened runtime с library validation требует подписи тем же Team ID (или ослабления через entitlement `disable-library-validation` — плохо для безопасности); в App Store запрещено |
| ExtensionKit (macOS 13+) | Приложение объявляет extension point, плагин — отдельный сандбоксированный процесс | Одобренная Apple модель; изоляция; пригодна для App Store; сторонние расширения возможны | Только Swift/ObjC; сложнее упаковка и отладка; неочевидно, как расширению проходят TCC-права (календарь) — нужен спайк; macOS-only |
| Внешний процесс + JSON-RPC по stdio | Хост запускает бинарник/скрипт, общается через stdin/stdout | Любой язык (Graph-коннектор на Python — за вечер); изоляция на уровне процесса; крэш-толерантность; **тот же протокол на Windows/Linux** | Сторонним авторам надо тащить рантайм (Python/Node) или собирать бинарник; вызовы EventKit из дочернего процесса неудобны (TCC приписывает запрос «ответственному процессу», но UX-подсказки и отладка страдают) |

Решение: **один контракт, два транспорта.**

- Первопартийные коннекторы, которым нужны Apple-фреймворки (EventKit, в будущем — что-то через Apple Events), — in-process, подписаны тем же Team ID, живут в репозитории приложения.
- Всё, что «ходит по сети» (Graph, Google Calendar API, CalDAV/ICS), и всё стороннее — внешний процесс по stdio.
- ExtensionKit держим как запасной вариант на случай App Store-сборки (A1).

Это одновременно и ответ на «переносимость»: сетевые коннекторы буквально те же файлы на Windows.

### 4.3 Изоляция и безопасность внешних плагинов

- Манифест плагина: имя, версия, исполняемый файл, список сетевых хостов, нужные сервисы хоста. Хост показывает пользователю, что плагин просит.
- Секреты не передаются через аргументы или окружение — только по RPC из Keychain и только short-lived токены; refresh-токен плагин не видит.
- Плагин не имеет доступа к БД и файлам приложения; всё, что он возвращает, валидируется по схеме.
- Таймауты и watchdog: зависший плагин убивается, ошибка показывается в UI.
- Подпись: сторонние бинарники должны быть нотаризованы, иначе Gatekeeper их заблокирует при запуске из приложения. Это реальное трение для «плагина на Python» — компромисс: официальный рантайм-плагин (например, `python-plugin-host`), поставляемый и подписанный вместе с приложением, который сам загружает пользовательские `.py`.

### 4.4 Первые коннекторы

**Outlook для Mac.** Четыре маршрута:

| Маршрут | Что даёт | Проблемы |

### 5.2 Рекомендованная конструкция

Два источника, одна временная шкала:

- **Системный канал** — process tap на **группу процессов** клиента созвона. Не на один PID: до версии 0.8 документ писал «для браузерных созвонов тапаем процесс браузера», и это **опровергнуто измерением** (MEE-8, R1). Tap на главный процесс Chrome даёт −200 dBFS — не поймано ничего; звук издаёт `com.google.Chrome.helper` (audio service, один на весь браузер). У Safari звук издаёт `com.apple.WebKit.GPU` — XPC-сервис с ppid 1, чей bundle id общий для всех WebKit-приложений. Tap на группу ловит весь звук (−27,0 dBFS у Chrome, −15,0 у Safari). Прежняя конструкция не записала бы **ни одной секунды** браузерного созвона, а это основной сценарий продукта. **Чем определяется группа процессов — контракт C-009** (`ProcessMonitorPort`); здесь это факт и ссылка, а не правило: правило принадлежит владельцу C-009 и живёт в одном месте.
- **Микрофонный канал** — устройство ввода по умолчанию.
- Оба подключены к одному **aggregate device** (tap как sub-tap, микрофон как sub-device, drift compensation на tap включена всегда) → один IO-callback → буферы обоих каналов с общим временем. Замер подтвердил, что компенсация дрейфа нужна и на встроенных устройствах: tap без неё уходит на −32…−35 мс/ч, с ней совпадает с часами источника до 0,0 ppm.
- **«Микрофон = я» — посылка, которая без обработки не выполняется.** До версии 0.8 документ писал, что диаризация и атрибуция опираются на «микрофон = я». Замер R6 (MEE-8): эхо собеседника из динамиков в микрофонном канале — **−31,1 dBFS**, и **голос пользователя на 1,9 дБ тише этого эха**; в двойном разговоре эхо добавляет +4,7 дБ; корреляция огибающей микрофонного канала с речью собеседника — 0,68. Инвариант «каналы не смешиваем» при этом не нарушен: файлы физически раздельны. Опровергнута именно посылка — **`channel == .mic` сам по себе больше не означает «говорил пользователь»**. Практическое следствие: ASR на сыром микрофонном треке расшифрует собеседника и припишет его пользователю, и ни одна проверка формата этого не поймает. Отсюда обязательный шаг конвейера — следующий пункт и §6.3, шаг 1. На этой посылке стоят C-003 (инвариант 5 — «на микрофонном канале говорит пользователь, диаризация там не нужна») и C-015 (`micChannel` как «единственный стопроцентный сигнал», `confidence == 1.0`); правка обоих контрактов вынесена в `interface-request`, потому что они не принадлежат этой правке документа.
- **Раскладка файла:** по файлу на канал — `audio-mic.*` и `audio-system.*` в каталоге записи (§8.1, решение по MEE-30; до версии 0.8 здесь по недосмотру оставалось «многоканальный контейнер, каналы 1–2 — микрофон, 3–4 — система», что противоречило и §8.1, и C-002). Каналы **не смешиваем**: смешанный файл уничтожает самый надёжный сигнал атрибуции и ухудшает диаризацию.
- **Формат на лету:** PCM в чанкованный CAF (заголовок допускает неизвестную длину — крэш посреди записи не теряет уже записанное; AAC через `AVAssetWriter` до финализации нечитаем). После финализации — транскод в AAC/Opus для хранения, временная 16 кГц моно-копия каждого канала для движка.
- **Поведение tap:** `muteBehavior = unmuted` (пользователь продолжает слышать собеседников), `isExclusive = false`.
- **Жизненный цикл:** процесс созвона завершился → tap инвалидируется → корректная финализация; смена устройства ввода или его формата → пересборка aggregate device с маркером разрыва; сон системы → пауза и маркер; пробуждение → попытка продолжить, если сигнал есть.
- **Пересборка временную шкалу не сохраняет — это измеренная неправда, и она заменена на число.** До версии 0.8 документ обещал «пересборку aggregate device с сохранением временной шкалы». Замер R2 (MEE-8, часовая запись 3659,9 с, две пересборки): после каждой пересборки содержимое сдвинуто относительно часов источника на **+149,6 и +144,0 мс**, за час накопилось **+293,6 мс**; внутри сегмента сдвиг стабилен до 0,01 мс; заполнение разрыва тишиной по host time первого буфера новой сборки ошибку не компенсирует. Дополнительно: сам файл идёт на +9,7 ppm быстрее mach host time (≈ +35 мс/ч), а взаимное смещение каналов на пересборке прыгает на ±20 мс. **Причина ухода шкалы не установлена** — ни спайком, ни разбором записи и кода в MEE-65; что известно и что её решает, названо в §5.5. Триста миллисекунд больше длины слова, а на этой же шкале стоят таймстампы транскрипта (C-003), поэтому величина названа **известным ограничением v1**, а не оставлена умолчанием: `discontinuity` в манифесте записи (C-002, издание 4) везёт длительность разрыва и оценку ошибки шкалы отдельными полями, чтобы потребитель мог вычесть её сам. Пока причина не найдена, любое утверждение вида «таймстамп точен до миллисекунды» после первой пересборки неверно.
- **Эхо: решение принято, вариантов больше нет.** Если пользователь без наушников, микрофон ловит голоса собеседников из динамиков. Спайк сравнил два пути на одной и той же речи, и выбор перестал быть вопросом вкуса.
  - **(а) `setVoiceProcessingEnabled(true)` — выключено по умолчанию навсегда.** Эхо оно действительно давит (−43,5 dBFS против −31,1; речь пользователя на 19,5 дБ громче эха). Решающий довод против — не окраска, а побочный эффект: включение voice processing **в любом процессе** переключает встроенный микрофон в 3-канальный режим **для всех клиентов** и глушит чужой звук на 8–30 дБ (ducking; 30,0 дБ по умолчанию, 8,0 дБ при `duckingLevel .min`). То есть наша запись ухудшала бы тот самый созвон, который записывает. Приложение, которое портит то, что наблюдает, наблюдателем не является. Настройкой этот путь быть не может по той же причине: цену платит не только запись, но и собеседники в реальном времени.
  - **(б) Сырой микрофон плюс подавление по корреляции с системным каналом — обязательный шаг конвейера, а не рекомендация.** Он единственный, что стоит между микрофонным треком и чужой речью в нём; место в конвейере — §6.3, шаг 1, до VAD и ASR.
  - **Факт среды, который мы не выбираем:** в Safari WebRTC сам переводит микрофон в режим voice processing на время звонка — наш канал приходит 3-канальным и около −60 dBFS (в Chrome — обычный 1 канал, −35 dBFS). Это делает чужое приложение, обойти это нечем; следствие — качество микрофонного канала на созвонах в Safari заведомо хуже, и в оценке WER это надо учитывать отдельно.

Абстракция для переносимости: протокол `AudioCapturePort` с операциями «перечислить процессы-источники», «начать сессию (источники, устройство ввода)», «поток буферов с раскладкой каналов», «события (разрыв, смена устройства)». Реализации: `CoreAudioTapCapture` (macOS 14.4+), `ScreenCaptureKitCapture` (fallback), позже `WasapiProcessLoopbackCapture` (Windows), `PipeWireCapture` (Linux). Именно этот интерфейс — а не libobs — является нашим «модулем захвата, переносимым между ОС».

### 5.3 Почему не libobs

1. На macOS OBS для системного звука сам использует ScreenCaptureKit (источник «macOS Audio Capture», OBS 30+). Обёртка вокруг libobs даёт ровно те же права и ограничения, что прямой вызов SCK, плюс десятки мегабайт зависимостей (FFmpeg и т. д.).
2. libobs — граф для видео-стриминга (источники, сцены, энкодеры, выходы). Нам нужен один аудио-путь; 90 % библиотеки — балласт.
3. Лицензия GPLv2. Линковка тянет за собой GPL на приложение; «арм-ленгс» через отдельный процесс формально возможен, но это ещё один процесс ради двух вызовов Core Audio.
4. Сборка libobs под macOS с нотаризацией и подписью всех dylib — отдельный проект.
5. Переносимость, ради которой OBS и рассматривался, достигается дешевле собственным `AudioCapturePort`: на Windows per-process loopback — штатный API, на Linux — PipeWire.

### 5.4 Браузерные созвоны

Meet и часто Teams живут во вкладке. Детекция: признак «издаёт звук» плюс занятый микрофон плюс окно события в календаре. Точность повышают заголовок активного окна через Accessibility (только если пользователь даст право — не обязательно) или расширение браузера (v2). **Важная поправка после MEE-8: признак «издаёт звук» у главного процесса браузера не поднимается** — `IsRunningOutput` равен 1 у helper-процесса, а не у браузера, и для Meet в Chrome и Safari сигнал по главному процессу не возникает вовсе. Чем именно детектор ловит браузерный созвон — контракт C-009; здесь только факт и ссылка.

Захват: tap на **группу** процессов браузера, а не на его главный процесс (§5.2). Ограничения, которые принимаем как известные в v1:

- audio service в Chrome один на весь браузер — в запись попадает звук всех вкладок и уведомлений; если параллельно играет YouTube, он попадёт в запись. VAD и диаризация отсеют музыку, речь из видео — нет;
- в группу может попасть звук постороннего приложения не по нашей воле — §5.5, пункт 1.

### 5.5 Что платформа не гарантирует

Раздел появился в версии 0.8 по итогам MEE-8. Здесь собраны свойства macOS, которые мы не выбираем и не можем обойти, но обязаны знать, планируя модуль `capture` и контракт `AudioCapturePort` (C-004). У каждого пункта — число и цена; где цены нет, сказано, чем она станет.

1. **HAL расширяет группу tap сам, и в запись может попасть чужое приложение.** При tap по pid GPU-процесса Safari HAL записал в описание tap `bundleIDs = ["com.apple.WebKit.GPU"]` и втянул GPU-процесс **другого** приложения (Handy, pid 1067) — bundle id у WebKit-процессов общий для всех WebKit-приложений. Это не курьёз, а свойство платформы с последствием для приватности: в системный трек попадает звук приложения, которое пользователь записывать не просил, и узнать об этом из записи он не может. Цена, пока это не закрыто: обещание «записываем только выбранный созвон» в интерфейсе давать нельзя — оно будет ложным; перечень процессов, попавших в tap, обязан доезжать до манифеста записи и быть видимым пользователю (C-002 это и делает полем `capturedProcesses`). Требование к C-004 сформулирует РП при выдаче задачи на него.
2. **Tap следует за bundle id и переживает перезапуск процесса** (macOS 26): HAL сам ставит `processRestoreEnabled = true`, и после перезапуска тапнутого клиента звук возвращается без пересборки — тишина ровно на время отсутствия процесса (измерено: 15–25-я секунда прогона). Следствие: `pid` в манифесте может не соответствовать ни одному процессу, чей звук есть в файле. На macOS 14.x этих свойств нет (`API_AVAILABLE(macos(26.0))`), поведение там не проверялось.
3. **Tap обязан жить дольше aggregate device.** Попытка пересоздать tap в момент смены формата микрофона даёт `AudioHardwareCreateProcessTap` → `noErr` **с нулевым id**, двадцать раз подряд по ~1,3 с на вызов; разрыв записи в этом прогоне — 27,4 с. С паузой в 1 с и новым UUID tap создаётся за 42 мс. Пересобирать при смене устройства следует только aggregate device.
4. **Уход временной шкалы на пересборке — причина не установлена.** Величина: +144…+150 мс на пересборку, +293,6 мс за час с двумя пересборками (§5.2). Что удалось сузить разбором записи и кода спайка в MEE-65: избыток тишины, записанной при заполнении разрыва (210 и 199 мс в системном канале), превышает фактический простой между последним буфером старой сборки и первым буфером новой (77 и 64 мс по журналу событий) на 133 и 135 мс — и это совпадает с измеренным сдвигом с точностью до одного-двух IO-буферов. То есть сдвиг вносит не новая сборка, а то, что к моменту разрыва файл **уже** короче, чем показывают часы: содержимое последних ~135 мс до пересборки до файла не доехало, а заполнение разрыва по host time превращает эту потерю в постоянный сдвиг всего, что идёт после. Гипотеза «tap отдаёт накопленное после пересборки» опровергается самими данными: взаимное смещение каналов на разрыве прыгает лишь на ±20 мс, то есть оба канала уехали вместе, а не системный относительно микрофонного. Вопрос решают два числа, которые спайк уже пишет в `events.log` часовой записи: `fileMinusHostClockBeforeBreakMs` на каждой пересборке и `sessionSamplesMinusHostMs` в последней сводке перед ней. Пока они не прочитаны, величина живёт в документе как ограничение, а в C-002 — как поле разрыва.
5. **Bluetooth-гарнитура не проверена.** У неё другой домен часов и 16/24 кГц; замена в спайке (смена формата встроенного микрофона) проверила пересборку aggregate, но не смену часового домена. Известный риск модуля `capture` (R16): смещение каналов на пересборке прыгало на ±20 мс уже на встроенном устройстве, на чужих часах оно может оказаться больше и не вернуться назад.
6. **`IsRunningOutput == 1` держится и при цифровой тишине** — признаком того, что звук действительно идёт, это свойство не является. Детектору его одного мало (C-009).
7. **Право на системный звук публичным API не читается.** Статус `kTCCServiceAudioCapture` до первой попытки создать tap неизвестен; как `permissions` его читает — контракт C-007. Разрешённый для этого приватный вызов и его цена — §9.4.

## 6. Транскрибация и диаризация

### 6.1 Локально или облако

| Критерий | Локально | Облако |
|---|---|---|
| Качество (RU/EN, шумные созвоны) | Whisper large-v3 / Parakeet v3 — очень хорошо; чуть уступает лучшим облачным на сложном звуке | Лидеры (ElevenLabs Scribe, AssemblyAI, Speechmatics, Deepgram) — лучшие метрики, особенно диаризация |
| Приватность | Содержание встреч не покидает машину — для многих организаций это условие использования вообще | Нужны DPA, согласие участников, оценка рисков |
| Стоимость | Ноль за минуту; разовые затраты на CPU/GPU | ~$0.2–0.6 за час, растёт с объёмом |
| Оффлайн / регион | Работает везде | Зависит от сети и доступности API в регионе пользователя |
| Скорость (час записи, M2 и новее) | Parakeet на ANE — минуты; Whisper large-v3-turbo на Metal — ~3–6 мин | Минуты, параллельно, без нагрева ноутбука |
| Поддержка | Модели, обновления, дисковое место (0.5–2 ГБ), совместимость с ОС | Смена цен и API, вендор-лок |
| Смешанные языки в одной встрече | Whisper — да; Parakeet — «по одному языку на сегмент», требует проверки на код-свитчинге | Обычно да |

Решение: **локально по умолчанию**, облако как ещё одна реализация того же интерфейса, включаемая пользователем явно. Ключевые причины — приватность содержания встреч (это самое чувствительное, что есть у пользователя), нулевая переменная стоимость и независимость от сети/региона.

### 6.3 Конвейер

1. **Подготовка.** Подавление эха в микрофонном канале по корреляции с системным — **обязательный шаг, а не опция** (§5.2: без него эхо собеседника в микрофонном канале громче голоса пользователя на 1,9 дБ). Затем ресемплинг каналов в 16 кГц моно и нормализация громкости. Шаг живёт там же, где 16 кГц моно-копии, — у `engine-xpc` (C-002 называет его владельцем этих копий); владение модулями и зависимости от этого не меняются. Критерий, по которому шаг считается работающим, задаёт спайк качества: WER на микрофонном канале записи, сделанной без наушников, не хуже, чем на записи с наушниками, а доля реплик собеседника, приписанных пользователю, — ноль на записи `76470457-960B-4D2D-8831-9E3E72B240D6` из MEE-8.
2. **VAD** по каждому каналу (Silero) → сегменты речи, отсев тишины и музыки.
3. **ASR** по каналам раздельно (микрофон и система) с пословными таймстампами. Раздельно — потому что модель не смешивает перекрывающуюся речь, а канал после шага 1 даёт «я / не я».
4. **Диаризация** только системного канала → кластеры + эмбеддинги. Основание — не «в микрофонном спикер известен по построению» (посылка опровергнута, §5.2), а то, что после шага 1 в микрофонном канале остаётся один говорящий. Если спайк качества покажет, что шаг 1 этого не обеспечивает, диаризация микрофонного канала перестаёт быть лишней — и тогда меняются C-003 (инвариант 5) и C-015 (правило 1).
5. **Выравнивание** слов ASR с кластерами по времени → сегменты «кластер N сказал …».
6. **Атрибуция** (§7) → сегменты «Иван сказал …».
7. **Уверенность текста.** Из CTC-вероятностей — уверенность каждого токена, из них — слова и сегмента (минимум по словам, не среднее: одно сомнительное имя важнее десяти уверенных предлогов). Хранится в `segments.text_confidence` и в пословном JSON; UI подсвечивает слова ниже порога и выводит их первыми в режиме правки.
8. **Постправка имён по участникам.** Из `attendees` встречи строится словарь имён: полное имя, имя, фамилия, транслитерация (Иван / Ivan), уменьшительные формы (Ваня) — из справочника `person_name_forms`, который пополняется вручную и по правкам пользователя. Неуверенные слова и спаны сверяются со словарём по нечёткому совпадению (расстояние по фонетической форме, не по буквам); замена делается только при уверенности ASR ниже порога и близости выше порога, оригинал сохраняется в JSON слова для отката. Замены помечаются `attribution_source = name_dictionary`, чтобы пользователь видел, что правил не человек.
9. **Резюме и извлечение итогов** — расширение, точка подключения закладывается в v1, реализация позже (§6.6).

Интерфейсы: `TranscriptionEngine.transcribe(audio, language?, wordTimestamps) → Transcript` (в `Transcript` — уверенность по словам, если движок её отдаёт; облачные движки — как есть или `null`), `DiarizationEngine.diarize(audio, numSpeakers?) → Segments + Embeddings`, `EmbeddingEngine.embed(audioSlice) → Vector`. Разделены, потому что лучшие ASR и лучшая диаризация часто у разных поставщиков; облачные вендоры могут реализовывать оба сразу.

### 6.4 Рекомендация

- **ASR для русского — GigaAM v3, вариант `e2e_ctc`** (пунктуация + покадровое выравнивание для таймстампов). **Решено (Q10): целевой исполнитель — ANE через CoreML, путь — через CPU-этап.** Этап 1: sherpa-onnx с официальной конверсией на CPU — эталонное качество без своей математики, замер реальной нагрузки, сбор тестового набора. Этап 2: CoreML-порт на ANE (свой mel, свой CTC-декодер, окна 25–30 с со сшивкой) против работающего эталона; после прохождения паритет-тестов становится реализацией по умолчанию в профиле, CPU-путь остаётся запасным на случай, когда CoreML-модель не компилируется на конкретной версии macOS. План Б, если конверсия упрётся в неподдерживаемые операции: GPU через MLX Swift (динамические формы, без окон, Conformer переписывается вручную).

**Размещение вычислений по ролям (итог):**

| Роль | Модель | Исполнитель | Рантайм |
|---|---|---|---|
| VAD | Silero | ANE | FluidAudio (CoreML) |
| Диаризация | pyannote community-1 | ANE | FluidAudio (CoreML) |
| Эмбеддинги голоса | WeSpeaker | ANE | FluidAudio (CoreML) |
| ASR английский | Parakeet TDT v3 | ANE | FluidAudio (CoreML) |
| ASR русский, этап 1 | GigaAM v3 e2e_ctc int8 | CPU | sherpa-onnx (ONNX Runtime) |
| ASR русский, этап 2 | GigaAM v3 e2e_ctc | ANE | свой CoreML-конвейер в XPC-движке |

Почему не начинать с CoreML: без работающего эталона неясно, где ошибка — в конверсии, в mel-признаках или в декодере. Почему не остаться на CPU: 3–5 минут полной загрузки всех ядер на час записи — на MacBook Air это вентилятор и батарея после каждой встречи. CoreML-провайдер ONNX Runtime как «средний путь» не рассматривается: на Conformer часть графа уезжает обратно на CPU, выигрыш непредсказуем.
- **VAD, диаризация, эмбеддинги — FluidAudio** (Silero, pyannote community-1 offline, WeSpeaker): языконезависимы, работают на ANE, эмбеддинги нужны для профилей спикеров.
- **ASR для английских встреч — Parakeet TDT v3 из FluidAudio**, выбирается профилем транскрибации.
- **Полностью смешанные встречи** (длинные англоязычные фрагменты в русской встрече) — v2: языковой роутер по VAD-сегментам (LID → GigaAM или Parakeet). В v1 — профиль на встречу; английские термины внутри русской речи GigaAM берёт сам.
- **Whisper (whisper.cpp)** остаётся в каталоге как запасной вариант для языков вне GigaAM/Parakeet и как участник бенчмарка; не в v1.

**Изучено: как GigaAM сделана в Handy (`transcribe-rs`, модуль `onnx/gigaam`).** Вариант `v3_e2e_ctc`, одиночный ONNX-файл (int8 — 225 МБ) + `vocab.txt` на 257 BPE-токенов; экспорт от istupakov (onnx-asr). Рантайм — ONNX Runtime (`ort`) на CPU, фича `ort-coreml` есть, но выключена. Конвейер: 16 кГц моно → mel на своём коде (n_fft 320, hop 160, 64 мела, HTK) → одна ONNX-сессия → жадный CTC → склейка SentencePiece. Таймстампов и нарезки длинных файлов нет. Это решение под диктовку, не под встречи; копировать его не нужно.

**Наш движок GigaAM — что делаем иначе и лучше:**

1. Пословные таймстампы из кадров CTC (40 мс/кадр, группировка токенов по `▁`) — обязательны для выравнивания с диаризацией.
2. Длинные записи: нарезка по VAD на окна ≤ 25 с с перекрытием и слиянием на стыках; смещение окна добавляется к таймстампам.
3. Раздельная обработка каналов (микрофон / система) на общей временной шкале.
4. Уверенность по токенам из CTC-вероятностей → уверенность сегмента → подсветка сомнительных мест в UI и приоритет ручной правки.
5. Имена участников из календаря как словарь постправки: неуверенные спаны сверяются с именами по нечёткому совпадению.
6. Варианты модели как настройка профиля транскрибации: `e2e_ctc` по умолчанию, `e2e_rnnt` как режим качества.
7. Тесты на паритет с PyTorch-эталоном в CI: смена экспорта или рантайма (ONNX → CoreML) не должна менять результат незаметно. Экспорты sherpa-onnx и istupakov независимые, CTC детерминирован — сверка простая.
8. Аппаратный путь — ANE как цель, CPU как этап и запасной вариант (решено, Q10), а не умолчание рантайма.
- **Облачные движки** — реализации того же `TranscriptionEngine`, включаются пользователем явно; в UI живут в одном списке с локальными (§6.5).
- **До выбора движка — прототип конвейера на Python** (whisperX + pyannote) на 10–20 реальных созвонах: измерить WER на русском/английском, DER диаризации, точность атрибуции. Это самый дешёвый способ понять, какого качества вообще можно ждать, и выставить пороги; после этого нативный движок сравнивается с этим эталоном.

### 6.5 Model Manager и размещение движка

**Размещение движка — XPC-сервис.** FluidAudio работает в `Contents/XPCServices/TranscriptionEngine.xpc` — отдельном процессе, который launchd запускает при первом обращении и завершает после простоя. Приложение общается с ним через `NSXPCConnection`; протокол — те же `TranscriptionEngine` / `DiarizationEngine` / `EmbeddingEngine`, сообщения — `Codable`-структуры (`Transcript`, прогресс, отмена). Почему отдельный процесс, а не библиотека в приложении:

- память: модели занимают 1–2 ГБ, а базовый M2 — 8 ГБ, из которых Zoom и браузер уже забрали половину. После транскрибации XPC-сервис просто умирает, и память возвращается системе гарантированно, а не «когда ARC доберётся»;
- изоляция сбоев: падение инференса (битая модель, CoreML-ошибка, OOM) перезапускает сервис, а не приложение с идущей записью;
- ресурсы: у сервиса собственный QoS `.utility` и учёт `ProcessInfo.thermalState`; настраиваемое «только от сети» и «не во время записи» — на стороне Job Queue.

Цена — один дополнительный target в проекте и сериализация аудио-путей вместо передачи буферов; для пост-обработки файлов это не имеет значения. CoreML и ANE в XPC-сервисах работают штатно. Model Manager остаётся в приложении и передаёт сервису пути к моделям; сервис ничего не скачивает сам.

**Model Manager** — отдельный компонент приложения, отвечающий за каталог, загрузку, хранение и жизненный цикл моделей. Перед проектированием изучен модельный менеджер Handy (open-source диктовка на Tauri): там просто и понятно сделаны выбор, загрузка и удаление моделей. Наш дизайн — свой, под наши отличия: не одна модель, а набор ролей; часовые файлы; облачные движки в общем списке; профили транскрибации.

Каталог — данные, не код. JSON-манифест:

```
models[] {
  id, role: asr | vad | diarization | embedding,
  engine: fluidaudio | sherpaonnx | coreml-gigaam | whispercpp | ...,
  runtime: coreml | onnx,
  displayName, description, sizeBytes, languages[],
  url, sha256, version, quantization,
  minChip: m2 | m3 | ..., minRAMGB,
  recommendedFor[]: ru | en | mixed | fast | quality
}
```

Встроенная копия манифеста — в бандле как fallback; актуальная подтягивается с нашего CDN при запуске. Новая модель добавляется без релиза приложения.

Роли — главное отличие от Handy. У нас четыре слота: ASR, VAD, сегментация для диаризации, эмбеддинги голоса. В UI пользователь выбирает не модель, а **профиль транскрибации** — набор моделей по ролям плюс язык и параметры диаризации. Роли защищают от ситуации «удалил модель эмбеддингов — профили спикеров перестали работать, непонятно почему»: Model Manager знает, кто от кого зависит, и предупреждает.

Состояния модели: `available → downloading (прогресс, докачка) → downloaded → loaded → error`. Загруженная в память модель выгружается, когда очередь задач пуста; «downloaded» не значит «занимает RAM».

Хранение: `Application Support/<bundle-id>/models/<engine>/<model-id>@<version>/`. Удаление — удаление каталога плюс проверка зависимостей профилей. UI показывает занятое место по моделям.

Раздача: собственное CDN-зеркало, а не Hugging Face напрямую, — надёжность, контроль версий и работоспособность из сетей, где HF недоступен или медленный. Ручная установка задокументирована: положить файлы в каталог модели, перезапустить — модель появляется как «downloaded». Проверка `sha256` при загрузке и при ручной установке.

Автообнаружение кастомных моделей в папке `models/custom/` — с валидацией формата при загрузке; неподходящий файл показывается с ошибкой, а не роняет приложение.

Облачные движки — в том же списке, что локальные: у локальной модели кнопка «скачать», у облачного движка — «указать ключ». Одна ментальная модель для пользователя: «чем транскрибировать». Ключи — в Keychain.

Профили транскрибации вместо одной активной модели: например, «RU-встречи → Parakeet v3 + диаризация FluidAudio», «смешанная речь → Whisper large-v3-turbo». Профиль выбирается вручную или правилом по календарю (участники, название встречи). Это закрывает и проблему смешанных языков (A4).

Один и тот же XPC-движок держит два рантайма: CoreML (FluidAudio и, после этапа 2, GigaAM) и ONNX Runtime (sherpa-onnx для GigaAM на этапе 1 и как запасной путь). Для Model Manager это поле `runtime` в манифесте; для сборки — ещё один набор dylib под подпись (§9.3). Модели GigaAM раздаются с нашего CDN в двух упаковках для одной роли: sherpa-onnx (encoder int8 + tokens) и CoreML-пакет; профиль выбирает упаковку по доступности, предпочитая CoreML.

Что проверить на спайке: FluidAudio должен уметь загружать модели из указанного нами каталога, а не только из собственного кэша, — иначе Model Manager придётся подстраивать под его раскладку.

### 6.6 Резюме итогов встречи — расширение

Решено (Q8): резюме понадобятся, но не в v1. В v1 закладывается точка подключения, чтобы добавить их без изменения конвейера и схемы.

**Точка подключения.** Протокол `PostProcessor` в XPC-движке: вход — `Transcript` с атрибутированными спикерами, метаданные встречи (название, участники, текст приглашения как повестка), профиль постобработки; выход — набор `MeetingOutput {kind, contentMarkdown, structured JSON?, engine, promptVersion}`. Виды выходов: краткое содержание, принятые решения, action items с ответственными (сопоставленными с участниками), открытые вопросы. Job Queue получает тип задачи `summarize`, который запускается после `attribute`. Фейковая реализация протокола входит в v1 вместе с остальными протоколами движка.

**Хранение.** Таблица `meeting_outputs` — meeting_id, kind, engine, model_version, prompt_version, content_md, structured_json, created_at, is_user_edited. Несколько версий на встречу: пересчёт другим движком или промптом не затирает предыдущее; правки пользователя помечаются и не перезаписываются автоматикой. Экспорт — тот же Markdown-бандл встречи.

**Движки — за тем же принципом «локально по умолчанию, облако по выбору»:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| Локальная LLM через MLX Swift или llama.cpp (модели с хорошим русским: Qwen3, YandexGPT-Lite, T-lite, Vikhr — выбор по бенчмарку на своих транскриптах) | Приватность, ноль за встречу, оффлайн | На базовом M2 с 8 ГБ — только модели 3–4B в 4-бит; качество резюме ниже облачного; ещё один рантайм в XPC-движке |
| Облачная LLM (GigaChat, YandexGPT, OpenAI, Anthropic) | Качество, длинный контекст, ничего не грузить | Содержание встречи уходит наружу; ключи, доступность в регионе |
| Apple Foundation Models (macOS 26+) | Бесплатно, встроено | Набор языков и доступность по регионам — проверить; для русского на момент написания неочевидно |

**Что учесть в реализации.** Длинные встречи не помещаются в контекст малых моделей — map-reduce по блокам с сохранением спикеров; промпт получает список участников для правильных имён в action items; результат пересчитывается, если пользователь переименовал спикеров после генерации; запуск в XPC-движке после ASR, чтобы память LLM освобождалась гарантированно. Версионирование промптов обязательно: без него нельзя понять, почему резюме стало хуже после обновления.

**Что нужно решить перед реализацией:** локальная модель или облако по умолчанию; формат action items (свободный текст или структура с ответственным и сроком); нужна ли интеграция с внешними заметками (Obsidian, Apple Notes, Linear) — экспорт или прямая запись.

## 7. Привязка спикеров к участникам

Диаризация выдаёт анонимные кластеры «спикер 1, 2, 3». Превращение их в имена — вероятностная задача, и честно её нужно проектировать как таковую, с уверенностью и ручной коррекцией.

Сигналы по силе:

1. **Канал микрофона = пользователь — после подавления эха.** Сильнейший из сигналов, и поэтому каналы не смешиваются (§5.2). Но «стопроцентным» он назывался ошибочно: в сыром микрофонном канале эхо собеседника из динамиков громче голоса пользователя на 1,9 дБ (замер R6, MEE-8), и без обязательного шага подавления (§6.3, шаг 1) он даёт неверную атрибуцию — уверенно и молча. Что это значит для порогов: `confidence == 1.0` у источника `micChannel` (C-015, правило 1) больше не обоснована измерением, и её пересмотр вынесен в `interface-request`.
2. **Голосовые профили.** После того как пользователь один раз назвал кластер («это Иван»), эмбеддинг сохраняется в профиль Ивана. В следующих встречах кластеры сравниваются с профилями **только участников этой встречи из календаря** (косинусное сходство, порог). Список участников сужает кандидатов с «все, кого я знаю» до «эти пять» — это главная польза календаря для атрибуции.
3. **Встречи 1:1.** Единственный не-микрофонный спикер = второй участник. Тривиально и часто.
4. **Текстовые подсказки.** Самопредставления («это Андрей»), обращения по имени («Иван, что скажешь?» → следующий спикер вероятно Иван). Реализуется LLM-постпроцессором со списком участников в контексте; средняя сила.
5. **Сигналы платформы** (v2): индикатор активного спикера в окне Zoom/Teams/Meet через Accessibility или расширение браузера; список участников из клиента. Хрупко, ломается с обновлениями клиентов, требует дополнительных прав — только как опциональный усилитель.

Каждое назначение хранит `confidence` и `source`. UI показывает неуверенные назначения как «Спикер 2 (возможно Иван?)», подтверждение одним кликом обновляет профиль. Профили версионируются по модели эмбеддингов — смена модели инвалидирует профили.

Важное следствие: голосовые эмбеддинги коллег — биометрические данные (GDPR, 152-ФЗ). Хранить только локально, с явным согласием пользователя на функцию, с возможностью удалить профиль. Это открытый вопрос в §10.

## 8. Хранение данных

### 8.1 Раскладка

```
~/Library/Application Support/<bundle-id>/
  db.sqlite                       — метаданные, транскрипты, очередь, профили
  recordings/<recording-uuid>/    — UUID записи, не встречи: запись бывает без встречи
    audio-mic.caf                 — микрофонный канал во время записи
    audio-system.caf              — системный канал во время записи
    audio-mic.m4a                 — микрофонный канал после финализации
    audio-system.m4a              — системный канал после финализации
    manifest.json                 — RecordingManifest (C-002)
    transcript.v<N>.json          — сырой выход движка (C-003), N с 1
  models/<engine>/<model>@<ver>/  — модели движков
  logs/
```

Три вещи в этой раскладке не самоочевидны, и каждая — следствие уже принятого решения, а не оформление.

**Каталог именуется идентификатором записи, а не встречи.** Отношение «встреча ↔ запись» не один к одному ни
в одну сторону: `meetingId` в манифесте опционален (ad-hoc созвон, который детектор поднял по факту звонка в Zoom
или в браузере, события календаря не имеет вовсе), а у одной встречи бывает несколько записей — созвон прервался
и перезвонили. При именовании по встрече для первого случая имя каталога не вычисляется, а во втором вторая запись
молча переписала бы `manifest.json` и аудио первой. Связь с встречей выражается внешним ключом
`recordings.meeting_id` в БД (§8.2) и полем `meetingId` в манифесте — обоим позволено быть пустыми.

**По файлу на канал.** Микрофон и системный канал не смешиваются никогда: смешанный файл уничтожает главный
сигнал атрибуции «я / собеседник» (§7). Один общий `audio.m4a` этому требованию противоречит буквально.

**Номер транскрипта в имени файла.** Переобработка другим движком или другой моделью создаёт новый транскрипт,
а предыдущие не удаляются (§8.2, таблица `transcripts`). С фиксированным именем `transcript.v1.json` второй
транскрипт стирал бы первый. Номер `N` присваивает `storage`; версия **схемы** файла живёт в его поле
`schemaVersion`, а не в имени.

### 8.2 База данных

SQLite через **GRDB.swift**: явная схема и миграции, поддержка FTS5, WAL, хорошая производительность, и та же схема без изменений открывается rusqlite/Python при переносе. Альтернативы: Core Data / SwiftData — Apple-only, неявные миграции, слабый контроль над запросами и поиском; Realm — фактически не развивается; «просто JSON-файлы» — нет запросов и поиска.

Таблицы (суть, не DDL):

- `meetings` — id, title, start, end, provider, join_url, organizer_id, status; `meeting_sources` — связь с внешними id коннекторов (одна встреча ← несколько источников).
- `persons` — id, display_name; `person_emails` — email → person (люди приходят из разных календарей под разными адресами); `person_name_forms` — person_id, form, kind (`full` / `first` / `last` / `translit` / `diminutive` / `user_added`) — словарь для постправки имён (§6.3, шаг 8), пополняется из календаря автоматически и из правок пользователя.
- `attendees` — meeting_id, person_id, response_status, is_optional.
- `recordings` — meeting_id, paths, started_at, ended_at, channel layout, captured bundle id, status.
- `transcripts` — recording_id, engine, model_version, language, created_at (несколько версий на запись — для переобработки другим движком).
- `segments` — transcript_id, start_ms, end_ms, channel, cluster, person_id?, speaker_confidence, attribution_source, text, text_confidence; пословный JSON в сегменте: `{start_ms, end_ms, text, conf, original?}` — `original` хранит слово до постправки именами; `text_original` на уровне сегмента — текст до любых автоматических замен (отдельная таблица `words` не нужна до появления функций «клик по слову»).
- `segments_fts` — виртуальная FTS5-таблица по `segments.text` (поиск по всем встречам, с ранжированием).
- `speaker_profiles` — person_id, embedding (BLOB), model_version, sample_count, updated_at.
- `jobs` — type, payload, status, attempts, run_after, error.
- `connectors` — id, type, settings_json, keychain_namespace, last_sync, cursor.
- `meeting_outputs` — meeting_id, kind (`summary` / `decisions` / `action_items` / `open_questions`), engine, model_version, prompt_version, content_md, structured_json, created_at, is_user_edited — резюме и итоги (§6.6); в v1 таблица создаётся пустой, чтобы миграция потом не понадобилась.

### 8.3 Форматы и политики

- **Аудио:** AAC 64–96 кбит/с на канал в `.m4a` (Opus в `.caf` — лучше по битрейту, но хуже совместимость при экспорте). Час записи ≈ 60–80 МБ.
- **Хранение сырого PCM** — нет: 16-битный стерео 48 кГц — это ~700 МБ/час.
- **Удержание:** настраиваемый TTL на аудио (например, 30 дней), транскрипты — бессрочно; отдельная политика на профили.
- **Шифрование:** в v1 полагаемся на FileVault (диск целиком) и права доступа к каталогу; опционально SQLCipher для БД и шифрование аудио, если появится требование «даже при доступе к файлам». Секреты — только в Keychain.
- **Экспорт:** Markdown/JSON/SRT/VTT по встрече; «бандл встречи» (папка recordings + выгрузка её строк) как единица переноса и будущей синхронизации.
- **Бэкап:** каталог попадает в Time Machine; синхронизация между устройствами — вне v1 (это уже бэкенд, см. A5).

### 9.2 Фоновая работа

- Menu-bar-приложение (`LSUIElement = YES`) — стандарт для этой категории; окна открываются по требованию.
- Во время записи: `ProcessInfo.beginActivity(.userInitiated, .idleSystemSleepDisabled)` — отключает App Nap и не даёт системе уснуть от бездействия; крышка ноутбука всё равно усыпит систему — обрабатываем через `NSWorkspace.willSleepNotification` (пауза + маркер).
- Во время транскрибации: QoS `.utility`, уважение теплового состояния, настраиваемое «только от сети».
- Обновления — Sparkle (вне App Store).
- Сборка только arm64 (без x86_64-слайса); проверка поколения чипа при первом запуске — `sysctl hw.perflevel0.name` / `machdep.cpu.brand_string` с предупреждением, если старше M2. Жёстко запретить установку на M1 средствами бандла нельзя.

### 9.3 Sandbox и дистрибуция

При A1 (Developer ID, hardened runtime, без sandbox) всё описанное работает. Если понадобится App Store-сборка:

- динамическая загрузка `.bundle`-плагинов невозможна → только ExtensionKit;
- дочерние процессы наследуют sandbox — внешние stdio-плагины формально возможны, но с сильными ограничениями;
- Apple Events требуют временных исключений в entitlements, которые ревью может отклонить;
- работоспособность process taps под sandbox не подтверждена — нужен спайк;
- доступ к файлам вне контейнера — только через security-scoped bookmarks (влияет на экспорт).

Hardened runtime и нотаризация обязательны и вне App Store: все dylib (ONNX Runtime и sherpa-onnx внутри XPC-движка), встроенные фреймворки (CoreML-модели FluidAudio, при необходимости whisper.cpp) и плагины должны быть подписаны; библиотечная валидация запрещает грузить чужие бинарники в процесс — ещё один аргумент за out-of-process сторонние плагины.

### 9.4 Приватные API: что разрешено и какой ценой

Спайк MEE-8 нашёл два места, где публичного API нет вовсе, а без ответа модуль работать не может:

| Вызов | Что даёт | Почему без него нельзя |
|---|---|---|
| `responsibility_get_pid_responsible_for_pid` | Связать процесс с приложением, которое за него отвечает | У `com.apple.WebKit.GPU` ppid равен 1, а bundle id общий для всех WebKit-приложений: связать GPU-процесс именно с Safari публичными средствами нечем (§5.2) |
| `TCCAccessPreflight` | Прочитать текущий статус права на запись системного звука | Публичного способа узнать статус до первой попытки создать tap нет; без него мастер прав не отличает «право не выдано» от «право выдано, но звука нет» |

**Решение: оба вызова разрешены для Среза 1.** Основание — A5 и A1: приложение для личного использования, не нотаризуется и не распространяется, членство в Apple Developer Program не оплачено, ревью Apple нет ни на каком этапе. То есть обычная причина запрета приватных вызовов — отклонение на ревью и отзыв подписи — здесь отсутствует.

**Цена записана прямо: любой из двух может отвалиться на обновлении macOS.** Требование к деградации, и это главное в решении: отказ приватного вызова обязан давать деградацию вида «Safari не поддерживается» или «статус права неизвестен, нажмите проверить», а **не** «пишем не тот звук» и не «молча ничего не записали». Первое пользователь видит и понимает, второе он обнаружит через неделю по пустому транскрипту. Отсюда правило по признаку, а не перечень случаев: **результат приватного вызова не имеет права быть единственным основанием для того, чтобы считать запись идущей или правильной** — каждый такой вызов имеет публичную проверку-подпорку (для tap это факт наличия звука в канале, для права — попытка создать tap), и именно она решает, писать ли и что показывать.

Конкретные места вызовов называют контракты C-009 (`ProcessMonitorPort`) и C-007 (`PermissionsPort`) — здесь решение уровня документа и его цена.

## 11. Предлагаемый порядок работ

1. **Спайк захвата (1–2 недели).** Swift-CLI: process tap + микрофон в aggregate device, чанкованная запись, тесты на Zoom/Teams/Meet, смена устройств, сон/пробуждение, kill -9. Снимает R1, R2, R6, R9.
2. **Спайк качества (параллельно, 1–2 недели).** Python-конвейер: официальный пакет `gigaam` (все четыре варианта) + Parakeet v3 + Whisper для сравнения, pyannote для диаризации — на реальных записях из спайка 1; метрики WER/DER/атрибуция; определить пороги и вариант GigaAM. Снимает R3, R4, задаёт эталон для нативного движка и тестовый набор для R13.
3. **Спайк рантайма GigaAM (2–3 дня).** GigaAM v3 через sherpa-onnx в Swift на базовом M2: скорость, нагрев, память, таймстампы. Снимает R12, R14.
4. **Спайк Graph (2–3 дня).** Регистрация приложения, MSAL-логин, `calendarView` с delta, проверка admin consent на целевом тенанте. Снимает R5.
5. **Скелет приложения.** Доменный пакет без AppKit-зависимостей, порты и адаптеры, SQLite-схема с миграциями, машина состояний с тестами, XPC-сервис движка с фейковой реализацией протоколов, Model Manager с манифестом и загрузчиком.
6. **Первая вертикаль.** EventKit-коннектор → детекция → запись → GigaAM v3 (sherpa-onnx) + диаризация FluidAudio → «я / собеседник» без профилей → просмотр транскрипта. Уже полезно для встреч 1:1.
7. **Этап 2 GigaAM: CoreML-порт на ANE** (1–2 недели) — против эталона из этапа 1 и тестового набора из спайка качества; критерий готовности — паритет по WER и таймстампам, энкодер на ANE по профилировщику, время на час записи и нагрев измерены на базовом M2.
8. **Дальше.** Graph-коннектор, профили спикеров, профили транскрибации (Parakeet v3 для английских встреч), облачные движки, языковой роутер для смешанных встреч, экспорт.
